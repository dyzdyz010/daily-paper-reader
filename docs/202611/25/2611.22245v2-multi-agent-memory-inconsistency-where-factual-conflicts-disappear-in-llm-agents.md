## 摘要
多智能体委托使 LLM 系统能够在具有独立上下文的多个工作智能体之间分配证据收集。这带来了一致性挑战：工作智能体检索到的事实，可能不会出现在主导智能体用于共同结论的证据中。我们引入了一个基准和证据流分析器，通过在 Harvey LAB 文件审阅任务中设置受控的事实冲突来研究多智能体记忆不一致性。在生成开销相当的情况下汇总三个模型，与单智能体执行相比，要求委托将两个冲突主张的检索率从 50.2% 提高到 68.7%，但冲突检测率却从 16.2% 下降到 13.2%。在该设置中，工作智能体仅对 35.2% 的已检索主张对同时报告两个主张；汇总的匹配比较显示，当一个工作智能体同时读取两个主张时，检测率高于单智能体执行，但当主张被拆分到不同工作智能体时，检测率更低。从工作智能体到主导智能体的交接是改进多智能体 LLM 冲突检测的核心目标。

## Abstract
Multi-agent delegation lets LLM systems distribute evidence collection across workers with separate contexts. This creates a consistency challenge: facts retrieved by workers may be missing from the evidence available to the lead for a joint conclusion. We introduce a benchmark and evidence-flow profiler for studying multi-agent memory inconsistency through controlled factual conflicts in Harvey LAB document-review tasks. Pooled across three models with comparable generation spending, requiring delegation increases retrieval of both conflicting claims from 50.2% to 68.7% relative to single-agent execution, yet conflict detection falls from 16.2% to 13.2%. Within this setting, workers report both claims for only 35.2% of retrieved pairs, and pooled matched comparisons show higher detection than single-agent execution when one worker reads both claims but lower detection when the claims are split across workers. Worker-to-lead handoffs are a central target for improving conflict detection in multi-agent LLMs.

# 论文总结：《Multi-Agent Memory Inconsistency: Where Factual Conflicts Disappear in LLM Agents》

## 1. 论文的核心问题与整体含义

- **研究背景**：多智能体 LLM 系统通过委派（delegation）将证据收集分布到具有独立上下文的多个 worker agent 上，由 lead agent 汇总。这种架构虽然能并行探索更多信息源，但带来了记忆一致性挑战：worker 检索到的事实可能不会出现在 lead 最终决策所依赖的证据中。
- **核心问题**：论文研究 **多智能体记忆不一致性（multi-agent memory inconsistency）**——任务相关证据是否在本地和共享状态之间保持可用，尤其是两个相互冲突的事实（例如同一财务数据出现两个不同数值）能否被完整保留并用于冲突检测。
- **整体含义**：委派虽然提高了证据检索覆盖率，却可能导致事实冲突在 worker-to-lead 交接中“消失”，最终降低冲突检测率。因此，不能仅用端到端任务准确率评估多智能体系统，需要分离证据检索、交接保留和最终合成。

## 2. 论文提出的方法论

- **基准构建**：
  - 在 11 个 Harvey LAB 文档审查（due-diligence）任务中注入受控的数值冲突。
  - 每个冲突通过将文档集合中反复出现的数值 \(A_i\) 替换为 \(B_i\) 来植入，同时在别处保留 \(A_i\)，从而形成相互矛盾的证据。
  - 共植入 **73 个受控数值冲突**，每个任务 5–7 个冲突。冲突规格、源位置、等价表示和评分标准由评估方单独保存，不提供给 agent。

- **三种委派策略**：
  - **None**：单 agent 自己阅读文档并撰写报告。
  - **Optional**：lead 可以自己阅读文档，也可以创建 worker 并分配任务，允许重叠审查；用于观察模型是否自发选择委派。
  - **Required**：lead 必须委派，只能通过消息协调和综合，不能直接阅读源文档；workers 检查分配好的文档分区。Optional/Required 最多允许 10 个并发 worker。

- **证据流 profiler**：
  - 通过本地代理捕获模型请求/响应，并关联 SDK 事件、工具输出、agent 轨迹和报告制品。
  - 将证据追踪划分为四个阶段：
    - **Source Reads**：源工具输出中出现的证据端点。
    - **Worker Reports**：worker 发出的消息/完成报告中的端点。
    - **Lead Evidence**：lead 收到的消息加上 lead 自己的源读取（None/Optional 下）。
    - **Final Report**：最终被评分的报告中的端点。
  - 使用统一 matcher 按事实锚点和等价表示识别端点。

- **Pair Recall 指标**：
  \[
  R_t^{pair} = \frac{1}{N}\sum_{i=1}^{N} \mathbf{1}\{ G_i \subseteq E_t^i \}
  \]
  其中 \(G_i = \{A_i, B_i\}\) 是冲突对，\(E_t^i\) 是第 \(t\) 阶段观察到的端点集合。若两个端点都出现，则该冲突获得 pair credit。
  - 在前三个阶段进一步分解为 **Same**（单个个体提供两个端点）和 **Split**（只有多个贡献者的并集包含两个端点）。
  - Final Report 是单一制品，因此只使用 Both，不做 Same/Split 分解。

- **语义判断**：
  - 使用 LLM judge（claude-sonnet-5）按 rubric 评分。
  - 每冲突两个标准：明确识别差异，并准确处理定量比较。
  - **Judge Pass** 要求两个标准均满足，用于衡量实际冲突检测率。

## 3. 实验设计

- **数据集/场景**：
  - 11 个 Harvey LAB 法律文档审查任务，任务要求审阅文档目录并撰写 red-flags 报告。
  - 在这些任务中植入 73 个数值冲突，所有冲突在同一任务中共享同一份报告进行评估。

- **模型与配置**：
  - 评估三个模型：GPT-5.6 Luna、GPT-6 Luna（通过 Codex SDK）、Claude Haiku 5.5（通过 Claude Code SDK）。
  - 每个模型在三种策略（None、Optional、Required）下各运行 2 次全部 11 个任务。
  - 总计 **198 次任务执行**，**1,314 个冲突观察**（每模型/策略 146 个，pooled 每策略 438 个）。

- **对比方法**：
  - 主要对比 **None vs Optional vs Required** 三种委派策略。
  - 还进行 **匹配队列分析**：按 Required 的 Source Reads 或 Lead Evidence 中的 Same/Split 证据分布，对同一模型、运行、任务和冲突实例在 None 与 Required 之间进行配对比较。

- **成本控制**：
  - 使用每任务每轮 **59.60 美元** 的公共生成预算。
  - 当花费低于配置阈值时，agent 会继续原生会话审查和修改报告。
  - 平均花费在预算的 0.95–1.02 倍之间；判断成本不计入预算。

## 6. 主要结果

- **证据流逐阶段衰减**：Source Reads 阶段的 Pair Recall 相对较高（尤其在 Required 策略下），但经过 Worker Reports、Lead Evidence 到 Final Report，Pair Recall 单调下降，说明冲突证据在从 worker 到 lead 的交接中被系统性丢弃。
- **委派策略对比**：Required 在 Source Reads 阶段能发现更多冲突，但其 Final Report 中的 Pair Recall 与 None 相比没有优势，甚至更低；Optional 下模型并非总是选择委派，但一旦选择委派，也会出现类似的冲突丢失现象。
- **Same/Split 分解**：在 Source Reads、Worker Reports 和 Lead Evidence 阶段，冲突对更多以 Split 形式存在（两个端点分散在不同 worker 的消息中），而 Final Report 作为单一制品，很难同时保留两个端点；Same 比例较低，说明单个 worker 很少同时报告冲突双方。
- **语义判断结果**：Judge Pass 率低于 Pair Recall，即使两个冲突端点都出现在最终报告中，模型也可能未明确识别差异或未准确处理定量比较。
- **匹配队列分析**：在相同模型、运行、任务和冲突实例下，None 策略的 Final Report Pair Recall 通常高于 Required，进一步支持“委派导致冲突消失”而非单纯检索不足。

## 7. 讨论与局限

- **委派的权衡**：委派提升了证据检索覆盖率，但代价是证据整合完整性下降；需要设计显式的冲突检测/汇总机制，或让 lead 在综合阶段保留更完整的中间证据。
- **局限性**：
  - 只覆盖数值冲突，结论未必能推广到语义冲突、时间线冲突或逻辑矛盾。
  - 任务领域单一（法律文档审查），其他领域（如医学、金融、科研）的表现未验证。
  - 每个模型/策略组合仅 2 次运行，随机性较大。
  - 闭源模型 API 的版本与行为可能随时间变化，且成本预算可能影响 agent 行为。
  - LLM judge 本身可能存在评分偏差。

## 8. 结论

论文提出并实证了 **多智能体记忆不一致性**：委派架构中，冲突事实在 worker-to-lead 交接和最终报告中容易“消失”，从而降低冲突检测率。作者建议将多智能体系统评估从端到端准确率扩展为分离的证据检索、交接保留和最终合成三个维度，并为后续设计更可靠的委派与冲突综合机制提供诊断工具和基准。
