## 摘要
执行长时程任务的LLM智能体会以反复出现的程序性方式失败。它们错误地对API进行分页、解析错误的实体，或在未被要求回答时作答。我们构建了一条流水线，让智能体从自身历史中学习。它首先从智能体自身的轨迹中挖掘简短的教训，每个回合一到三条。然后，它将这些教训整合为更小的一组指南，每条指南记录它合并了多少条教训。在推理时，智能体接收全部指南或一个选定的子集。该流水线已在开源altk-evolve库中发布，并部署在IBM的CUGA智能体和watsonx Orchestrate平台中。我们报告在构建、测量和产品化过程中所学到的经验。我们的主要工具是AppWorld基准，涵盖基线任务完成率从40%到92%的多个模型。核心发现是，合适的记忆量是模型自身的属性，而非记忆的属性。强模型随着指南的添加持续改进。DeepSeek-V3.2在使用其完整的191条指南集时，任务完成率提升9.5个百分点，场景完成率提升16.1个百分点。弱模型从相同的完整指南集中获得的提升少于从一个小型选定子集中获得的提升。gpt-oss-120b起始任务完成率为39.9%。使用全部199条指南时达到51.2%，但使用约29条的选定子集时达到55.4%（两次运行的平均值）。围绕这一结果，我们报告了出现的问题：一条高支持度的指南产生了反效果，整合过程中来源信息被静默丢弃，一个被吞掉的API错误导致每个任务失败却生成了看似合理的日志，以及一个基线混淆差点导致与先前方法产生误导性的比较。我们将这些提炼为部署智能体记忆的团队的建议。

## Abstract
LLM agents on long-horizon tasks fail in recurring, procedural ways. They mis-paginate an API, resolve the wrong entity, or answer when no answer was asked. We built a pipeline that lets an agent learn from its own history. It first mines short \emph{lessons} from the agent's own trajectories, one to three per episode. It then consolidates those lessons into a smaller set of \emph{guidelines}, where each guideline records how many lessons it merged. At inference the agent receives either all guidelines or a selected subset. The pipeline ships in the open-source altk-evolve library and is deployed in IBM's CUGA agent and watsonx Orchestrate platform. We report what we learned building, measuring, and productizing it. Our primary instrument is the AppWorld benchmark, across models spanning 40--92\% baseline task completion. The central finding is that the right amount of memory is a property of the model, not the memory. A strong model keeps improving as guidelines are added. DeepSeek-V3.2 gains +9.5 points of task completion and +16.1 points of scenario completion with its full 191-guideline set. A weak model gains less from the same full set than from a small selected subset. gpt-oss-120b starts at 39.9\% task completion. It reaches 51.2\% with all 199 of its guidelines but 55.4\% (mean of two runs) with a selected subset of about 29. Around that result we report what went wrong: a high-support guideline that backfired, provenance silently dropped during consolidation, a swallowed API error that failed every task while producing a plausible log, and a baseline confound that nearly produced a misleading comparison with a prior method. We distill these into recommendations for teams deploying agent memory.

## 1. 核心问题与整体含义

- **研究背景**：LLM 智能体在长时程、多步骤任务中反复出现程序性错误，例如 API 错误分页、解析错误实体、在未被要求回答时作答。这些不是知识缺口，而是可重复的程序性失误。
- **核心问题**：能否让智能体从自身的历史轨迹中自动学习，并将经验转化为可复用的记忆？以及，不同能力的模型到底应该接收多少记忆量？
- **整体含义**：论文报告了一条自蒸馏记忆流水线在真实产品（IBM CUGA 与 watsonx Orchestrate）中的构建、测量与部署经验。核心发现是：**合适的记忆量是模型自身的属性，而非记忆本身的属性**。强模型随指南增多持续受益，弱模型则可能被过多记忆淹没，而少量精选子集反而更好。

## 2. 方法论

论文提出的流水线名为 **altk-evolve**，包含三个阶段：

- **轨迹捕获**：通过三种方式获取智能体运行轨迹——直接插桩常见客户端库、从可观测性存储同步、或由智能体在任务结束时通过 MCP 工具提交轨迹。
- **教训提取（Extraction）**：
  - 对每个轨迹（成功与失败均保留），使用 LLM 提取 1–3 条简短、祈使式的教训，说明“下次应该怎么做不同”。
  - 教训的证据极性（成功或失败）来自任务评估器的实际结果，而非 LLM 的自我报告。
- **支撑守恒的整合（Support-conserving consolidation）**：
  - 将教训嵌入并聚类近重复项；仅在同一聚类内、且当遵循一条教训等价于遵循另一条时才用 LLM 合并。
  - 每条存活指南携带**支持计数**（即合并了多少条独立教训）以及证据极性。
  - 强制不变量：输出的支持计数总和等于原始教训数；未被 LLM 覆盖的教训原样保留。
  - 例如：DeepSeek-V3.2 的 290 条原始教训被整合为 191 条指南，其中 144 条支持度为 1。
- **推理时传递（Delivery）**：
  - 可静态注入全部指南，或通过检索选择子集。
  - 检索模式下，高支持度核心（支持度 ≥ 3）始终包含，再按源任务与当前任务的相似度补充 top-k 条指南，并去重。
  - 提供配置项：`consolidation_mode`、`min_support`、`core_support`、`retrieval_top_k`、`injection_mode`。
- **部署约束**：同一模型既执行任务，也用于提取与整合教训，无独立教师模型或人工标注，符合“从自身日志中改进”的真实部署场景。

- **指标**：
  - **TGC**：通过所有评估检查的任务比例。
  - **SGC**：场景中所有任务变体均通过的比例（更严格）。
- **智能体**：参考 ReAct 代码智能体，每步生成 Python 代码并由环境返回输出。
- **模型范围**：基线 8 个模型，其中 6 个模型运行了记忆流水线；基线任务完成率跨度 40%–92%。
- **对比方法**：
  - 与 **ACE**（Agentic Context Engineering）在相同模型和拆分上做对比。
  - 不同指南剂量的消融：0、12、19、47、47+10 retrieved、全部 191/199 条等。
  - 部署评估：CUGA 在 AppWorld 与 τ-bench 零售拆分上的表现；watsonx Orchestrate 的定性跨任务迁移示例。

## 6. 主要结论与发现

- **核心结论**：记忆量是模型属性。
  - 强模型（DeepSeek-V3.2）：指南从 0 增加到 191，TGC 从 79.8 升至 89.3（+9.5），SGC 从 64.3 升至 80.4（+16.1）。全部指南效果最好。
  - 弱模型（gpt-oss-120b）：全部 199 条指南得分 51.2，与 24 条核心指南的 53.6 差不多；最佳是约 29 条检索子集，得分 55.4（两次运行均值）。
  - 饱和模型（GLM-5）：87.5 有无记忆不变；过弱模型（Gemma-4-31B）：整体无提升。
- **七条关键洞察**：
  1. 合适剂量是模型属性：强模型多多益善，弱模型需要精选子集。
  2. 不要压缩记忆：价值在长尾、一次性、情境化教训；压缩成 12 条对 DeepSeek 只带来 +2.9，而全部 191 条带来 +9.5。
  3. 选择需要来源（provenance），而来源在整合中很容易丢失；必须作为不变量强制保存。
  4. 支持度衡量复发，不衡量正确性：一条高支持度分页指南曾导致任务回归，需人工修复。
  5. 先测量噪声底线再相信小 delta：固定配置两次运行得分相差 1.2 个任务；同一模型大量任务在两次运行间翻转。
  6. 在固定 scaffold 上比较方法并报告 tokens：与 ACE 对比时，两者基线不同，按提升幅度看贡献相当，而 token 成本差异巨大。
  7. 静默失败比建模问题更耗时：被吞掉的 HTTP 错误、输出截断、代理断连、写路径 bug 等。
- **部署建议**（7 条）：将剂量作为一等参数；无损整合、传递时选择；强制下游排序字段为上游不变量；增加正确性/新鲜度信号；建立噪声底线；固定 scaffold 比较并报告 tokens；假设失败是静默的并设置断言。

## 7. 优点

- **真实的部署经验**：不是纯学术 benchmark，而是来自 IBM 产品（CUGA、watsonx Orchestrate）的工程实践，开源 `altk-evolve` 库。
- **反直觉、有价值的发现**：否定了“记忆越多越好”的简单假设，揭示了模型能力与记忆剂量之间的非单调关系。
- **支撑守恒不变量**：设计上保证整合过程不丢失教训数量，为后续选择提供可靠依据。
- **关注失败与噪声**：专门报告“出了什么问题”，包括错误指南、来源丢失、静默失败、基线混淆等，具有高度工程参考价值。
- **成本透明**：在每个表格中报告 token 成本，展示记忆注入的推理开销，便于部署决策。
- **可重复性意识**：在噪声分析中重复运行，明确低于噪声的 delta，避免误导。

## 8. 不足与局限

- **算力信息缺失**：没有报告 GPU 硬件、并行方式、总计算时长，无法评估复现成本。
- **单次运行为主**：多数结果基于单次运行，统计显著性不足；虽然作者讨论了噪声，但未对所有关键比较做多次重复。
- **测试集配置选择有偏差风险**：部分“最佳配置”是在 `test_normal` 上直接选择的，可能导致过拟合。
- **模型与任务范围有限**：主要基于 AppWorld 一个基准；部署评估只覆盖 CUGA 和 τ-bench 零售场景，watsonx 仅一个定性示例。
- **弱模型提升机制不明确**：虽然观察到弱模型需精选子集，但未深入解释为何全量指南有害，也未系统探索选择策略。
- **缺少自动化维护机制**：系统本身无法识别错误、过时或矛盾的指南；高支持度错误指南需人工修复，限制了无人值守运行。
- **部分结论基于少量模型**：如“强模型持续受益”“弱模型需少记忆”主要来自 DeepSeek-V3.2 和 gpt-oss-120b 两个典型，普适性有待更多模型验证。
