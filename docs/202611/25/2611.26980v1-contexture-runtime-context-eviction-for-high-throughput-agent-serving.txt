## Abstract 

LLM agents such as Hermes, OpenClaw, and Codex repeatedly re-send growing execution histories, increasing shared GPU key-value (KV) cache demand in high-bandwidth memory (HBM). We show that shared KV capacity limits agent-serving throughput. Existing context-reduction methods lack global cache-state visibility, while runtime KV managers lack tool-execution information. Tracing tokens to their originating tool operations reveals that later oper-ations supersede earlier outputs and associated turns, identifying 64% of recorded final-history tokens as removal candidates. We present Contexture, a harness- and model-agnostic architec-ture for runtime context eviction. Contexture separates the har-ness’s full conversation history from the model’s execution con-text, reducing subsequent requests’ KV demand without modifying harness logic or model execution. It combines tool-execution in-formation with global visibility into shared KV pressure and prefix residency: supersession identifies removal candidates, while run-time state determines when removal justifies sacrificing cached computation. This coordination reduces memory demand and de-code KV traffic while limiting re-prefill interference with concurrent decoding, without additional model calls or training. Across two models, two harnesses, and two benchmarks, Contexture improves throughput under SLO by 20–73% over the best of no eviction, harness compaction, AgentDiet, and Continuum, and by 7–63% over observation masking in five of eight configurations, and re-duces GPU energy per completed session by up to 11%. It also raises throughput under SLO by 23% over LMCache alone on H100. Live-agent experiments show a mean accuracy improvement of 1.4 percentage points over unloaded no eviction, with a worst-case loss of 3.7 points, while observation masking loses 3–28 points. 

## 1 Introduction 

LLM agents such as Hermes [36], OpenClaw [41], and Codex [40] perform multi-step tasks by repeatedly inspecting files, executing commands, and processing the resulting observations with LLMs. These interactions accumulate into a session history that is carried into subsequent model requests and can amount to hundreds of thousands of tokens [4, 47]. To avoid recomputing growing ses-sion histories, the serving runtime retains their reusable KV prefix caches in shared GPU high-bandwidth memory (HBM), where con-current sessions compete for finite cache capacity. Our key observation is that shared KV capacity is the critical bottleneck that limits agent-serving throughput. As more sessions arrive, the session completion rate stops increasing once the avail-able KV cache capacity is exhausted. Beyond this point, the runtime preempts requests and recomputes their KV caches, consuming ad-ditional compute without increasing completed-session throughput. Halving the KV pool of an H200 GPU reduces peak throughput by about 40%. These observations motivate reducing the KV memory occupied by each session to increase serving capacity. Existing approaches address growing KV memory demand at different levels of the agent-serving stack. At the harness level , com-paction [38, 41] and LLM-driven history editing [66] shorten session histories, but operate with a local view that lacks information about shared memory pressure and cached KV residency. Their model judgments consume GPU time and energy, delaying session com-pletion. They may also remove information the agent still needs. At the model level , KV pruning selects tokens based on attention scores within a request [5, 24, 73] or across a session’s turns [23], while other approaches require training to identify obsolete his-tory [19, 64, 72]. These methods do not account for shared KV memory pressure when deciding what to remove. At the runtime level , KV cache management has a global view of shared mem-ory [9, 22], but cannot shorten the session history, so evicted KV may be regenerated on subsequent requests. These approaches leave a coordination gap between identifying removable history and deciding when its removal is worthwhile given shared KV pressure and cached-prefix residency. Closing this gap requires identifying historical context that later agent operations have superseded. We characterize redundancy in the KV cache by tracing historical tokens to their origins in agent

Such supersession identifies 64% of the tokens in the final histories of our recorded sessions as removal candidates, without additional LLM calls. Each request exposes these candidates to the runtime, but removing them raises two challenges. A superseded observa-tion may still support ongoing agent actions. Removing an earlier span also invalidates subsequent cached KV, introducing re-prefill that interferes with concurrent decoding. Eviction must therefore balance reduced memory demand against lost cache reuse. 

Our work. We present Contexture, a harness- and model-agnostic architecture for runtime context eviction that combines origin-based context eviction with global cache-aware eviction . Contexture separates identifying removal candidates from deciding when to commit them. It uses tool operations and their targets to identify superseded outputs and associated turns, without additional model inference. Candidates remain available for a configurable grace window, giving the agent additional rounds to complete related actions before removal. For each request, Contexture combines eligible candidates with the runtime’s global view of shared KV pressure and cached-prefix residency across sessions. If no cached KV follows the earliest re-moval point, it commits immediately: the next request would need to recompute that suffix anyway, so removal reduces work without sacrificing cache reuse. Otherwise, Contexture defers removal until memory pressure warrants freeing capacity and limits the cached computation invalidated relative to the context removed. This co-ordination makes eviction responsive to both the demand from concurrent sessions and the cost of losing reusable computation. The harness retains its full conversation history, while the run-time filters the execution context processed by the model. The shortened prompt uses the engine’s ordinary prefix reuse and re-prefill, preserving exact execution over the retained context. This separation reduces subsequent KV demand and decoding work without modifying harness logic or model execution, or requiring additional model calls or training. We implement Contexture in vLLM [20] and evaluate eight con-figurations spanning two models, two harnesses, and two bench-marks on H100 and H200 GPUs. Contexture improves throughput under SLO by 20–73% over the best-performing baseline among no eviction, default and tuned compaction, AgentDiet, and Contin-uum. At the corresponding baseline SLO throughput, Contexture reduces p90 session slowdown by 30–78%. Compared with obser-vation masking, Contexture achieves 7–63% higher throughput in five configurations; masking performs better in the other three, all with Qwen MoE, but incurs 3–28 percentage points of accuracy loss across all configurations. With Qwen MoE and Hermes on Terminal-Bench, Contexture retains its gains with larger HBM ca-pacity and KV offloading, improving throughput by 14% over no eviction on H200 and 23% over LMCache alone on H100. It also reduces GPU energy per completed session by 8–11% at high load. Live-agent experiments across eight configurations and three loads show a mean accuracy gain of 1.4 percentage points over unloaded no eviction, with a worst-case loss of 3.7 points. ## 2 Background: Agentic Stack and Workload 

Figure 1 illustrates the agent-serving stack, where an agent harness interacts with an LLM through a serving runtime. The harness, such as Hermes [36], OpenClaw [41], or Codex [40], sends model requests to a serving runtime such as vLLM [20]. The runtime serves requests from multiple agent sessions on shared GPUs. Its API server receives incoming requests, the scheduler batches them for model execution, and the KV cache manager allocates KV blocks from a shared GPU memory pool. The model processes each request and produces reasoning, text, and tool calls conditioned on its history. The harness executes returned tool calls, such as shell commands, file reads, and file writes, in the session’s tool sandbox and incorporates their outputs into the conversation history. We define a model request together with its ensuing tool execution as a round , and the sequence of rounds belonging to one task as a 

session . Each session runs its own harness instance. Across successive rounds, each request carries the session’s ac-cumulated conversation history, which we call its logical context .Consecutive requests share an increasingly long prefix. With prefix caching, the KV cache manager retains the KV of processed tokens in GPU memory after a request finishes, allowing the next round to prefill only its new suffix. This reuse depends on the preceding context remaining unchanged and its KV states remaining cached. Removing an earlier context span changes the prefix of subsequent tokens, invalidating their cached KV states and requiring the surviv-ing suffix to be prefilled again. These KV blocks occupy a finite pool shared by concurrent sessions and remain idle while the harness ex-ecutes tools. As sessions progress, their growing histories increase demand for this shared pool. When the pool fills, the runtime evicts cached blocks or preempts running requests, causing later requests to recompute KV states that are no longer resident.

## 3 Agent Context and KV Management & Limitations of Existing Approaches 

We review context and KV management (§3.1), establish the shared-KV capacity bottleneck (§3.2) and examine limitations of three existing methods (§3.3). We replay recorded sessions of Hermes [36] on Terminal-Bench 2.1 (TB2.1) [34] at increasing load, served by vLLM [20] with Qwen3.8-27B [54] (§6.1). Throughput is the number of sessions completed within their task budgets per minute, and 

throughput under SLO is the throughput where their p90 slowdown relative to each task’s unloaded no-eviction run reaches 10 ×.

## 3.1 Managing Agent Context and KV 

Management of agent context and KV states spans three levels of the serving stack: the harness, model, and serving runtime. Each level operates on different states and has a distinct scope of control. 

Harness. The harness constructs the logical context for each round from the session’s conversation history, deciding which earlier messages and tool outputs the model sees. It can shorten this his-tory in several ways. Compaction replaces older history with an LLM-generated summary [3, 38, 40, 41]; observation masking [25] replaces older tool outputs with placeholders while retaining the agent’s reasoning and actions; and LLM-driven history editing asks a model which parts to remove [66]. These methods reduce subse-quent requests’ context length and KV demand. 

Model. Given the context assembled by the harness, model-level management uses information derived from model computation or training to identify tokens and their corresponding KV states for retention or removal. Representative examples include attention-based KV pruning and learned context selection [5, 19, 24, 73]. These methods make selection decisions at the token level within individual requests. 

Runtime. Once the model has computed the KV states, the serving runtime manages their residency across concurrent sessions. It determines which cached states remain in GPU memory, are evicted, or are moved to other memory tiers. Representative mechanisms include KV eviction, offloading, and retention [9, 10, 22]. ## 3.2 KV Capacity Bounds Agent Serving 

We examine how shared KV capacity affects agent-serving through-put as the load increases. Fig. 2 shows that without context eviction, throughput rises to 0.59 sessions/min before saturating, while p90 slowdown reaches 6.0 ×. The throughput peak coincides with KV pool saturation, which first occurs at 0.56 sessions/min. As the load increases, preemptions rise to 140 per run, causing repeated KV recomputation without increasing throughput. To further examine the impact of KV capacity, we reduce the KV pool from 1.5M to 1.0M and 0.76M tokens on the same H200. Peak throughput drops to 0.45 and 0.35 sessions/min, respectively. These results establish shared KV capacity as a limiting factor for agent-serving throughput. 

## 3.3 Existing Methods Fall Short 

We test three representative methods from the harness and run-time levels of §3.1 that need no training: Hermes compaction [38] replaces older history with an LLM-generated summary at a 128K-token threshold (§6.1); AgentDiet [66] uses LLM reflection calls to identify and remove unnecessary history; and Continuum [22] retains KV across tool executions for reuse by the next request, without shortening its history. Fig. 3 shows that none improves throughput under SLO over no eviction. Continuum’s curve lies on no eviction’s. Compaction’s and AgentDiet’s p90 slowdowns are above no eviction’s at every load shown, and served unloaded, their p90 is 2.2 × and 4.2 × no eviction’s. We study each method’s runs and identify three causes. 

Session-local decisions miss shared KV pressure. Compaction and AgentDiet decide from one session’s logical context, while KV demand comes from all sessions. KV retention does not reduce context demand. Continuum manages KV residency across concurrent sessions, but its retention policy leaves the logical context submitted in subsequent requests unchanged. Consequently, these requests continue to demand KV for the same history. 

LLM-driven logical context reduction is costly and fallible. 

Compaction and AgentDiet shorten the history with a model’s judgment. A model can weigh what the agent may need again, but its judgments on the serving GPU cost GPU time and energy, and the harness waits for each one before the session’s next request. In our recordings, a compaction summary call stalls its session for a median of 91 s. AgentDiet’s reflection call, 11 s at the median, runs before 60% of agent requests in the median session, and served unloaded its sessions take 1.5 × as long as no eviction’s. The model’s judgment in both methods can remove file contents from the session history that the agent still needs, forcing re-reads (Fig. 5). Lifting the limit calls for both a selection signal without extra model calls, to decide what to remove, and a global view of shared KV pressure and cached-prefix residency, to decide when. §4 shows that the serving runtime can provide both. 

## 4 Opportunities and Challenges 

Reducing shared KV pressure through context eviction requires identifying removable logical context and deciding when to re-move it. These decisions depend on agent execution history, shared runtime state, and the effects of removal on subsequent execution.

At no eviction’s peak throughput, marked spans of in-flight requests account for an estimated 30% of the shared KV pool’s capacity when occupancy reaches at least 95% (Fig. 6(b)). ## 5 System Design 

Contexture performs context eviction within the serving runtime, using tool-operation supersession to identify removal candidates and KV cache state to decide when to remove them. Its design follows four goals derived from opportunities and challenges in §4: 

G1 Global visibility into shared KV state : use the runtime’s view of shared KV pressure and cached-prefix residency across sessions to decide when to evict context. 

G2 Semantic selection through tool-operation supersession :identify superseded tool outputs and their turns from execution history without model calls, keeping the context that later actions need. 

G3 Harness- and model-agnostic context eviction : shorten only the prompt the model executes, in the runtime, without modifying the harness or the model and without training. 

G4 Bounded cache invalidation and re-prefill interference :avoid unnecessary recomputation and bound the cached com-putation each eviction sacrifices relative to the context it re-moves.

## 5.1 Overview 

Fig. 8 shows how Contexture processes each request between the API server and the unmodified scheduler. Each request carries the session’s full history and a session ID. The Session Evictor retrieves the session’s removal candidates , and its Policy Actuator uses shared KV pool occupancy and the candidates’ cached-prefix residency to decide whether to commit their removal or defer it (§5.3, §5.4). The 

Context Filter then removes all committed spans from the prompt before scheduling (§5.5). The harness keeps its full history, while the model processes the filtered prompt. After dispatch, the Session Tracker processes the request’s new tool messages asynchronously and marks earlier outputs that later operations supersede as candidates (§5.2). Each commit decision therefore uses candidates from earlier requests, which keeps track-ing off the critical path. Only a session’s first request, or one whose earlier history changed, waits for tracking. 

## 5.2 Tracking Superseded Context 

The Session Tracker semantically identifies removal candidates from the agent’s execution history without model calls (G2). For each request, it processes only the new messages and records each tool operation’s type, target, and outcome. 

Observing tool operations. To continue a session, the harness includes each tool call and its output in the next model request. The tracker therefore extracts tool operations directly from requests without accessing the harness or tool sandboxes. A tool call’s name and arguments identify the operation and its target. File tools name file paths, and the tracker parses shell command lines to find the programs they run and the files they read or write. Each tool output is linked to its call and records the outcome. A new harness or tool only extends the mapping from tool names and argument fields to operations. Calls to external services, such as web APIs and MCP servers, are tracked the same way. 

Supersession rules. The tracker matches later tool operations to earlier outputs by operation type and target (Fig. 9(a)). A later read or edit of a file supersedes earlier observations of it. Rerunning a normalized shell command supersedes its previous output, and a later run or build supersedes earlier run or build outputs whose 

> 5Hong et al.

target files overlap. Failed outputs are not superseded by unrelated operations, and a test result is superseded only when a rerun of the same test passes. Once all tool outputs of a round are superseded, the round’s tool calls and reasoning also become candidates. An unmapped tool’s output is superseded only by a repeat of the same call or a later run over a file the call names; otherwise it stays. The system prompt and task description are always retained. 

Grace window. Candidates become mature , and eligible for commit, only after a configurable grace window, 2 rounds by default (§6.4.1). The window keeps recently superseded information while the agent completes related operations, such as verifying an earlier edit. We evaluate the sensitivity of Contexture to it in §6.4.1. 

Locating spans. To remove a span, Contexture must know where each message lies in the token prompt that the chat template renders. The tracker renders the conversation a second time with the new message’s content blanked and takes the window where the two renders differ as its span, which leaves the template’s tool-response markers intact. Because tracking is asynchronous, spans come from an earlier prompt. The filter removes a span only while the current prompt still matches that prompt up to the span’s end. Otherwise, the request waits for tracking. 

## 5.3 Eviction Timing from Global KV State 

Contexture uses the runtime’s global view of shared KV state (G1) to decide when mature candidates are removed. Pool pressure de-termines when reducing context demand is beneficial, and cached-prefix residency determines whether a removal sacrifices reusable computation. The pressure gate and cold commits use these signals to avoid unnecessary re-prefill (G4). 

Pressure gate. When a removal would invalidate cached states, Contexture defers it until the shared KV pool is under pressure. With memory to spare, the invalidation adds computation without relieving capacity. Under pressure, removing superseded context reduces the KV demand of later requests, which admits more con-current sessions and avoids preemptions. Pressure is the fraction of KV blocks held by running requests, with a configurable thresh-old of 80% by default. We evaluate Contexture’s sensitivity to it in §6.4.2. Cached blocks of idle sessions are excluded because the allocator can reclaim them on demand. This global pressure signal coordinates eviction across sessions, while each session applies eligible removals at its next request. 

Cold commits. When the cached prefix ends before the earliest removal point, the next request recomputes the uncached suffix regardless, e.g., after cached blocks are reclaimed during tool ex-ecution. Committing cuts this recomputation without sacrificing cache reuse, so Contexture makes such cold commits regardless of pressure. 

## 5.4 Cache-Aware Commit Policy 

To balance context reduction against lost cache reuse (G4), Contex-ture groups a session’s matured candidates into one batch (Fig. 9(c)). The batch’s gain is the number of prompt tokens it removes. Since each prefix-cache block depends on all preceding tokens, the batch’s 

cost , the cached tokens whose reuse it invalidates, equals the num-ber of cached tokens after the earliest removal point, or zero if the cached prefix ends at or before that point. Candidates after the earliest removal point therefore add gain without adding cost. 

Residency probe. The cached-prefix length changes at each engine step as sessions run and the allocator reclaims idle blocks. The API server cannot compute it because the engine chains block hashes with a per-process seed, so Contexture adds a read-only 

residency probe to the engine’s KV cache manager. The probe hashes a session’s prompt block by block, as the scheduler does, and looks the hashes up in the GPU prefix cache. It neither allocates blocks nor modifies cache state, and the Policy Actuator invokes it only when a session has a matured batch. 

Commit rule. The Policy Actuator commits a batch whose cost is zero regardless of pressure (a cold commit, Fig. 9(b)). Otherwise, it commits only when pool pressure exceeds the threshold and the cost is at most the gain times a configurable re-prefill cap , 6 by default. We evaluate sensitivity to the cap in §6.4.3. For hybrid models, vLLM saves the recurrent states of linear-attention layers only at block-aligned engine-step boundaries. Re-prefill therefore starts from the last saved state before the cut, so the cost is a lower bound on the recomputation (Fig. 7). The cold-commit condition remains exact because a cached prefix ending before the cut also ends at a saved recurrent state. Context-window commits and tracker failures (§5.5) bypass the cap. A batch that fails these conditions stays pending until the session’s next request. 

## 5.5 Eviction Mechanism 

To keep eviction harness- and model-agnostic (G3), the runtime removes committed spans from the model’s input only, keeping the prompt structure valid and the prefix cache consistent. 

Prompt filtering. The Context Filter removes committed spans from the token prompt after chat template rendering and before scheduling. For tool outputs, it removes their content while retain-ing the template’s tool-response markers; committed assistant turns are removed entirely. The filter also excludes previously committed spans from every subsequent request, preventing their reintro-duction from breaking prefix-cache reuse. The harness keeps and resends its full history, while the model receives the shortened prompt. The harness only adds a session ID to each request. 

Cache interaction. The shortened prompt follows the engine’s normal prefix-caching mechanism. The committing request reuses the cached prefix before the earliest removal and re-prefills the rest (Fig. 9(d)). Subsequent requests extend the shortened prompt and reuse its cached states. Context removal does not immediately release GPU memory. The removed spans’ cached blocks are no longer referenced and are reclaimed through normal cache eviction. Shorter prompts reduce the KV demand of subsequent rounds and the KV entries read by full-attention layers for each generated token, lowering decode memory traffic. 

Request handling. Contexture checks the context window after filtering, so committed removals count before the engine applies the model’s context limit. If the prompt and output budget would still exceed the limit, Contexture commits the session’s matured candidates regardless of pressure and the re-prefill cap. If the res-idency probe times out, the batch stays pending and the request proceeds with earlier commits. The probe’s reading can be stale by the time the scheduler admits the request, but only in one direction. 

> 6Contexture : Runtime Context Eviction for High-Throughput Agent Serving

A session has at most one request in flight, so other requests can only reclaim its idle blocks. A stale reading thus only overstates the cost, so a pressure-driven commit stays within the re-prefill cap and a cold commit stays cold. If candidate tracking fails, the request runs unmodified with its full history, re-prefilling from the earliest restored span. It is rejected only if it exceeds the context window. 

## 5.6 Implementation 

We implement Contexture in vLLM 0.26 [20] with about 7K lines of Python. The Session Tracker and Session Evictor hook into vLLM’s OpenAI-compatible API server between chat-template rendering and scheduling. The tracker runs on a worker thread and parses shell commands with Python’s shlex . The prototype has superses-sion rules only for sandbox and file tools; external and MCP services are out of scope. The residency probe adds fewer than 100 lines to the engine core, which answers probes between execution steps. It is the only engine-core change, and the scheduler, KV cache alloca-tor, and model execution are unchanged. Pool usage comes from vLLM’s existing stat logger, which records the scheduler’s usage at each step. Each request carries its session ID in an agent_tracker 

field, which Hermes and OpenClaw forward through configuration. Per-session tracking state lives in host memory in a single API server process. 

## 6 Evaluation 

We evaluate Contexture across eight configurations spanning two models, two agent harnesses, and two benchmarks. We first compare its throughput under SLO against existing context-management and KV-management baselines, including observation masking (§6.2.1). We then evaluate its energy efficiency and task accuracy (§6.2.2, §6.2.3). Ablation and parameter-sensitivity experi-ments examine the contributions and robustness of its design (§6.3, §6.4). Finally, we evaluate Contexture with larger HBM capacity and KV offloading, and measure its request-path overhead (§6.5, §6.6). 

## 6.1 Experimental Setup 

We evaluate Contexture on two long-horizon agent benchmarks, two open-source agent harnesses, and one dense and one mixture-of-experts (MoE) model deployed on two GPU generations under varying load, and report throughput, latency slowdown, energy efficiency, and task accuracy. 

Workloads and platforms. We evaluate Contexture on two long-horizon agent benchmarks, Terminal-Bench 2.1 (TB2.1) [34] and SWE-Atlas-QnA (SWE-Atlas) [55], using their default task verifiers and rubrics, respectively. Both benchmarks comprise long-horizon tasks whose sessions reach 100K to 228K tokens of context at p90. We run two open-source agent harnesses, Hermes v2026.10.11 [61] and OpenClaw v2026.7.1 [41], on both benchmarks. The experi-ments use a dense model, Qwen3.8-27B [54], on an H200 GPU and an MoE model, Qwen3.6-35B-A3B [53], on an H100 GPU. Both mod-els use FP8 weights and vLLM 0.26 [20], with KV pools equivalent to six to seven full 262K-token contexts. They use hybrid linear and full attention (§5.4). 

Baselines. We compare Contexture against no eviction, production harnesses’ compaction, tuned harness compaction, observation masking, and academic works: LLM-driven history editing and runtime KV retention. These are the harness- and runtime-level methods (§3.1) that run on original Hermes and OpenClaw, require no model training, and support hybrid-attention models we serve: 

• No eviction retains the full history except when the harness han-dles context overflow. 

• Default compaction follows each harness’s shipped trigger. Her-mes compacts when a prompt reaches 75% of the input capacity after reserving output tokens (172K tokens) [37], while OpenClaw compacts only upon context overflow. These triggers depend on context length rather than KV pressure and are reached by 16% of no-eviction sessions in Hermes and 7% in OpenClaw, on average. 

• Tuned compaction lowers the default trigger to compact more sessions. We consider thresholds reached by more than 16% of no-eviction sessions, the higher of the two defaults’ mean reach, but by fewer than 40%, as more aggressive compaction reduces accuracy [18]. For each configuration, we select the threshold that completes the most tasks within their task budgets in unloaded recordings. 

• Observation masking [25] replaces every tool output except the 10 most recent with a short placeholder, without model calls. Hermes and OpenClaw ship variants [38, 42]. We implement it in vLLM’s request path, so both harnesses run unmodified. 

• AgentDiet [66] uses a reflection call to the agent’s own model on the serving GPU to reduce history, and is ported from Trae Agent [63] to both harnesses. 

• Continuum [22] uses the authors’ published implementation, whose default retains a completed request’s KV cache for 2 s when the tool’s mean execution time is shorter than 2 s. Contexture uses the same default parameters across all configura-tions: a pressure threshold of 80%, a re-prefill cap of 6, and a grace window of 2 rounds (§5). We evaluate Contexture’s sensitivity to them in §6.4. 

Load generation. We use trace replay to make the workload re-producible across load sweeps and repeated runs. Fixing agent trajectories, output lengths, and tool delays prevents run-to-run variation in generated work from confounding measurements of serving performance; scheduling, caching, and Contexture’s evic-tion decisions still respond dynamically to load. We first record each task’s session, including its prompts and tool execution times, for each harness, model, and baseline that changes the conversa-tion, and then replay these recordings. Compaction and AgentDiet replay their own recordings, which capture their context modifica-tions and additional model calls; these do not depend on load, so we replay each request by its prompt and output lengths, keeping the prefix it shares with the one before. Since Contexture makes eviction decisions based on shared KV pressure, its throughput experiments replay no-eviction recordings with their full prompts, from whose content it selects what to evict, with eviction applied dynamically at runtime. No eviction, Continuum, and observation masking, which masks outputs at runtime, replay the same record-ings, so all four start from the same recorded request sequence at each load. Replay preserves the recorded requests, output lengths, and inter-request gaps, including tool execution time. Sessions ar-rive according to a Poisson process [22, 31], with identical arrival schedules across policies at each load level. A session’s task budget

## 6.4 Parameter Sensitivity 

We evaluate the sensitivity of Contexture to each parameter using the workload in §6.3. We vary one parameter at a time while keeping the others at their default settings. 

6.4.1 Selection: Grace Window. The grace window delays the re-moval of superseded context for a configurable number of rounds. This gives the agent time to complete actions that may still depend on earlier outputs, such as verifying an edit (§5.2). We compare windows by task accuracy at High, where Contexture commits the most context. The default 2-round window achieves the highest accuracy at 88%, 2 percentage points above no eviction (Fig. 14(a)). Shorter windows reduce accuracy by 2–4 points, as they may re-move context before the agent finishes using it. Longer windows reduce accuracy by 6–7 points because they retain stale context for more rounds. 

6.4.2 Pressure Gate: Threshold. The pressure threshold determines when Contexture begins committing removals that invalidate cached prefixes. We compare thresholds, and re-prefill caps below, by passing sessions per minute, calculated as throughput under SLO multiplied by task accuracy at High. As shown in Fig. 14(b), the default threshold of 80% achieves 5–6% more passing sessions per minute than thresholds of 70% and 90%, and 27% more than no eviction. Throughput under SLO differs by only about 1% across the three thresholds because they remove similar fractions of the prompt near peak load. The 80% threshold achieves 4 percentage points higher accuracy, accounting for its higher passing-session rate.

## 6.5 Generalization to HBM Expansion and KV Offloading 

A larger HBM capacity delays KV-pool saturation, while KV of-floading lowers the cost of reclaiming GPU memory. We evaluate whether Contexture retains its gains under both conditions. We serve Qwen MoE with Hermes on an H100 and an H200 using the same recordings, arrival schedules, and task budgets. The two GPUs provide comparable compute but differ in KV-pool capacity, with 1.75M (4.44M) tokens on the H100 (H200). Contexture improves throughput under SLO by 32% on the H100 and 14% on the H200 (Fig. 15(a)). The smaller gain on the H200 is consistent with the reduced impact of KV capacity on serving throughput. Shorter con-texts reduce the KV-cache reads required during decoding, easing memory-bandwidth pressure even before the KV pool is full (§6.3.1). KV offloading keeps evicted KV in host memory and reloads it when its session resumes, instead of prefilling it again (§3). We add LMCache v0.5.7 [26] to no eviction and Contexture on the H100, configured per its recipe [30] with a 100 GB host tier. Offloading raises no eviction’s throughput under SLO by 29%(Fig. 15(b)); Con-texture alone reaches 2% more. With offloading, Contexture still gains 23% (22% with Qwen on the H200, where offloading adds 16% to no eviction). Offloading cuts the cost of evicting KV, but a running request still holds and attends over its full context on the GPU; Contexture shortens that context, so the two are composable. 

## 6.6 Overhead 

We measure Contexture’s request-path overhead across both mod-els, benchmarks, and harnesses at their highest probed loads. Across requests, Contexture adds a median delay of 30 ms before engine execution, accounting for 0.2% of request time at the median. Com-mit decisions and prompt filtering take a median of 9 ms, while 69% of requests also wait a median of 25 ms for a residency probe. The engine answers these probes between forward passes, so the me-dian wait is shorter than one forward pass over the batched prefill and decode tokens. The Session Tracker maintains its per-session state in host memory. Its host-memory footprint per tracked to-ken is well under 1% of the GPU KV memory required per token. Contexture introduces no additional GPU computation beyond the re-prefill caused by its commits. 

## 7 Related Work 

Agent context management. Harnesses shorten session histories through threshold-based summarization [3, 38, 40, 41, 43], obser-vation masking [25, 33], file-aware removal [7, 27, 60], or model-guided editing [18, 56, 66, 67]. These methods do not coordinate removals with shared KV pressure and prefix residency. Model-guided editing also incurs additional model calls and can discard information the agent still needs [66]. TokenPilot [67] maintains a provider’s prompt cache across a continuous task stream, but relies on cache hit and miss counts rather than runtime cache state. Most harness-integrated methods require adapting to each har-ness’s history format and hooks [8, 15, 52]. Pichay [33] performs masking through an API proxy but lacks visibility into the serving runtime’s KV pool. Contexture operates in the runtime, directly accesses shared KV pressure and prefix residency, and requires only a mapping from tool names to operation types for each new harness (§5.2). It extends supersession to commands, builds, and tests, and coordinates removal timing with shared KV state. 

Model-level KV reduction. Model-level methods keep the KV of high-attention tokens within a budget, some guided by cross-turn intent [5, 23, 24, 28, 65, 73], fetch only the KV predicted to mat-ter [21], or train a model to find stale history [19, 59, 64, 72]. They approximate attention or need model-specific training. Contexture is model-agnostic: it needs no training and keeps exact attention over the context it retains. KV quantization [16, 29] is orthogonal: it shrinks each token’s KV rather than the number of tokens. 

Runtime KV management. Serving runtimes reuse cached prefixes [20, 75], offload KV to host memory, SSDs or remote stores [10, 13, 26, 50, 69], evict cached blocks by predicted reuse or recompute cost [9, 44, 57, 74], and retain or prefetch a session’s KV across tool calls and workflow steps [1, 22, 45, 71]. They de-cide where KV resides but leave the history unchanged, so states needed again must be reloaded or recomputed. Contexture removes superseded history, which lowers the KV that later requests need and that memory tiers must store or move, and it uses the pool’s pressure and cached prefixes to decide when to commit each re-moval. Autoscalers (ServerlessLLM [12], BlitzScale [70]) scale the aggregate serving capacity, while load balancers (Llumnix [58]) distribute sessions across instances to manage KV load and cache locality. Contexture complements these mechanisms by reducing the KV demand generated by each session. 

Efficient context edits. Other work makes an edit’s re-prefill cheaper. Prompt caching and span removal from cached KV [11, 14, 17, 32, 56, 68] reuse states computed under a different preceding context. Leyline [32], for example, deliberately keeps downstream states influenced by the removed content, so its result differs by design from re-prefilling the edited prompt. supports only MLA attention, and AKV [11], concurrent with this work, uses one-token KV pages in its evaluated implementation and does not yet support the linear-attention layers of the models we serve. SmoothAgent [46] keeps edits exact by scheduling their re-prefill ahead of time within available latency slack, which can limit this benefit at high load. Contexture selects superseded his-tory from tool executions and uses shared KV pressure and prefix residency to decide when to commit each removal, paying an exact re-prefill. Exact execution of the retained prompt is separate from task accuracy, which depends on what is removed. 

## 8 Conclusion 

We present Contexture, a runtime context-eviction system that identifies superseded agent history through tool operations and coordinates removal with shared KV pressure and cache residency. Across eight configurations, Contexture improves throughput un-der SLO by 20–73% over the strongest of no eviction, compaction, AgentDiet, and Continuum, reduces GPU energy per completed session by up to 11%, and maintains task accuracy within 3.7 per-centage points of unloaded no eviction. These benefits persist with larger HBM capacity and KV offloading, while context reduction also lowers KV-read traffic during decoding.
