Abstract
LLM agents alternate between inference and tool execution, re-
peatedly reusing their growing context across calls. Under high
concurrency, their combined key-value (KV) cache working set can
reach hundreds of GiB, far exceeding GPU memory capacity. As
idle KV cache blocks are evicted to slower storage tiers, returning
agents incur expensive retrievals that stall inference.
To address this problem, we present TripleKV, a three-tier KV
cache management system that hides the delays of these retrievals.
In agentic workloads, the KV blocks needed by the next inference
request are known in advance; only the time of their reuse is uncer-
tain. TripleKV uses a tool-aware latency predictor to estimate when
each tool call will complete and prefetches the required KV blocks
from SSD into host DRAM ahead of time. Unlike GPU prefetching,
this avoids reserving scarce GPU memory and interfering with con-
current inference requests. To further improve DRAM utilization,
TripleKV eliminates duplication of GPU-resident blocks in DRAM,
and introduces a victim-cache mechanism that refills blocks from
SSD upon their eviction from GPU memory.
Across data, web, and coding agents, TripleKV reduces the frac-
tion of requests requiring critical-path SSD reads from 45–76% to
under 10%. It also reduces P95 time to first token (TTFT) by up to
49% compared with vLLM extended with DRAM and SSD KV-cache
tiers, and achieves 1.5-7× lower P95 TTFT than recent agent-aware
systems.

LLM Serving, KV Cache, Agentic AI, Memory Tiering, Prefetching

Introduction
LLM agents have fundamentally changed the workloads handled by
inference servers, with ReAct (Reasoning and Action) [37] emerg-
ing as the de facto standard for AI agents solving complex tasks.
ReAct-style agents alternate between LLM inference and tool calls
(e.g., web searches, page visits, and shell commands), submitting
their growing context as part of each new inference prompt (Fig. 1).
As a result, agent contexts can grow to tens of thousands of to-
kens. To avoid recomputing these tokens, inference engines retain
previously computed tokens in key-value (KV) caches, and reuse
them across inference calls through prefix caching [17]. For Qwen3-
30B-A3B [28], a popular 30B-parameter mixture-of-experts model,
the KV cache requires approximately 96 KiB per token. A single
50K-token agent context therefore occupies 4.6 GiB. On an NVIDIA
H100 NVL, model weights and runtime overhead leave roughly 32
GiB for KV caching, enough for only about six such contexts. Bal-
ancing KV cache reuse against GPU memory utilization is therefore
critical to serving performance.

While an agent executes a tool call, its previously computed KV
cache blocks may remain idle in GPU memory up to 100 seconds
or more, awaiting the next inference request. Meanwhile, other
agents compete for the same limited memory capacity, forcing
serving engines to evict cached blocks, either discarding them or
offloading them to host DRAM and potentially to slower storage
tiers [19, 24, 27] (Fig 2).
Many KV cache management systems rely on Least Recently
Used (LRU) policies for eviction. However, as we will show, LRU is
poorly suited to agentic workloads even under moderate system
load. Long tool execution intervals expose an agent’s idle KV blocks
to memory pressure from other agents’ inference requests, likely
evicting them before the agent resumes inference. In our experi-
ments, up to 76% of inference requests find their previously cached
blocks already evicted to slower tiers or discarded entirely. When
the agent resumes inference, these blocks must either be retrieved
from slower storage, potentially taking several seconds for a 50K-
token context, or recomputed through an expensive prefill phase

if discarded. Both introduce substantial delays, with recomputa-
tion additionally consuming GPU compute resources that could

Recent proposals explore different agent-aware strategies to
manage KV caches. Continuum [18] pins KV cache blocks in GPU
memory throughout tool execution. This approach avoids reloads
but occupies scarce GPU memory and limits throughput. Token-
Cake [6] instead offloads KV blocks to host DRAM during tool
execution. Later, it prefetches them back into GPU memory based
on predicted tool latency. However, our observations show that
prefetching into the GPU can be counterproductive: it competes
with inference requests for GPU memory, increasing queueing de-
lays. Further, mispredictions waste precious GPU memory capacity
on blocks that are not reused. Finally, while vLLM [17] is not agent-
aware, it is worth mentioning because it is popular. vLLM supports
SSD-backed KV caching to extend capacity beyond GPU and host
memory. This avoids nearly all recomputation, as SSD is typically
larger than the working set. However, retrieving evicted blocks from
SSD can place storage I/O on the critical path of inference. Overall,
existing approaches trade GPU memory capacity for reuse, risk
contention and wasted GPU memory capacity through prefetching,
or incur costly on-demand retrieval from slower tiers.
This paper approaches agent-aware KV cache management as
a classical multi-level caching problem, where GPU HBM, host
DRAM, and SSD are the three levels of the KV cache hierarchy. Our
proposal is called TripleKV. TripleKV relies on timely prefetching
of KV cache blocks from SSDs to host DRAM. TripleKV includes
three mechanisms: Predict, Prefetch, and Protect. First, a tool latency
predictor estimates when each tool call will complete and schedules
prefetching ahead of time to hide the expected storage read latency.
Second, a prefetch engine transfers the agent’s KV blocks from SSD
to DRAM, using lower priority than read requests from inference
calls. Finally, a prefetch-aware cache replacement policy protects
prefetched blocks in host DRAM from premature eviction.
TripleKV is built on top of vLLM [17]. It does not prefetch directly
into GPU memory because doing so introduces contention and
queueing delays. Instead, when an agent resumes inference, vLLM’s
existing request admission mechanism retrieves the prefetched KV
blocks from DRAM. TripleKV relies on tool call information to
timely prefetch KV cache blocks before an agent’s next inference
request. Traditional hardware prefetchers must predict both what
data will be accessed and when. In agentic workloads, the next
data to access is known; what is not known is when a tool call will
complete. Hence, TripleKV uses predictors. We find that tool calls
are typically long enough to hide SSD reads.
We evaluate TripleKV on four recent agentic benchmarks: Deep-
Research Bench (DRB) [9], GAIA [22], Terminal-Bench 4.0 (TB4) [21],
and Browse Comp-Plus (BC+) [8]. We run up to 20 concurrent
agents on an NVIDIA H100 GPU. TripleKV reduces the fraction of
requests requiring critical-path SSD reads from 45–76% to under
10%. It also reduces P95 time to first token (TTFT) by up to 49%
compared with vLLM extended with DRAM and SSD KV cache
tiers, and achieves 1.5-7× lower P95 TTFT than recent agent-aware
systems. Finally, it approaches the performance of an oracle with
perfect knowledge of tool call completion times.
This paper makes four contributions:
• The TripleKV agent-aware KV cache management system that
relies on predicting tool latencies and prefetching required KV
cache blocks to host DRAM.
• Characterization of KV cache behavior during agentic inference.
• KV cache block prefetching into host DRAM rather than GPU
memory, combined with agent-aware cache eviction and replace-
ment policy to prevent premature eviction.
• Evaluation of TripleKV, comparing to state of the art agent-aware
baselines on latency, throughput, and cache metrics.

Background
2.1
Agents Reuse Context at Every Step
ReAct-style agents exhibit substantial context reuse across consecu-
tive inference requests (Fig. 1). In all the representative benchmarks
we study (Sections 3, 6.1) prompts can reach 100K tokens, and a
single task can involve up to 100 LLM calls. Yet, each turn typically
adds only 1.0K–2.5K new tokens. Thus, consecutive requests from
the same agent share nearly their entire prefix, making KV cache
reuse particularly important for efficient inference serving.
Serving engines exploit this reuse through prefix caching [30].
Popular engines such as vLLM [17] and SGLang [42] store previ-
ously computed attention keys and values (KV cache) in fixed-size
blocks, identified by hashes that incorporate both their contents and
preceding prefix. When a new request arrives, the engine reuses
matching blocks from the beginning of the prompt, computing only
the remaining uncached suffix. In agentic workloads, 84.6–99.5% of
input tokens hit the prefix cache when capacity is sufficient [39],
while studies of multi-turn chat report that up to 99% of prefill work
involves previously processed context [11]. In ReAct-style execu-
tion, each subsequent inference request follows the completion of
a tool call, making tool completion the event that triggers reuse of
the agent’s existing context.
Observation 1. Agent inference requests repeatedly reuse large, con-
tiguous KV cache prefixes. The blocks required by an agent’s next re-
quest are largely known in advance, and their reuse is triggered by the
completion of its current tool call
2.2
The KV Hierarchy
By default, vLLM stores KV cache blocks only in GPU memory.
When a request completes, its blocks are placed on a free list but
retain their contents and identities for future reuse. New allocations
reclaim blocks from this list in Least Recently Used (LRU) order,
effectively using available GPU memory as a cache of previously
computed prefixes.
vLLM also supports tiered KV caching, extending GPU memory
(L1) with host DRAM (L2) and external storage (L3). The hierarchy
follows a write-through policy: completed KV blocks are copied
to lower tiers while retaining their copies in faster memory. We
use SSD as the external tier, with several terabytes of capacity,
effectively eliminating L3 evictions. This three-tier hierarchy serves
as our baseline (Table 1). Both GPU memory and DRAM use LRU
replacement. When an inference request arrives, vLLM first checks
for reusable blocks in GPU memory, retrieving missing blocks from
DRAM or SSD as needed. SSD-resident blocks must first be loaded
into DRAM before being transferred to GPU memory over PCIe.

Unlike conventional processor caches, KV cache blocks are enor-

block is missing from all tiers, subsequent blocks cannot be reused
as part of that prefix and must be recomputed. vLLM retrieves
blocks on demand, only after the inference request arrives, without
exploiting information about the agent’s ongoing tool execution.

2.3
Agent-aware KV Cache Management Systems
In this subsection, we discuss existing agent-aware KV cache man-
agement systems. We also include vLLM as it is very popular.
While an agent executes a tool, its KV cache sits idle, and serving
systems must decide where to keep it until the agent returns. Exist-
ing systems make one of three choices. vLLM [17] evicts the idle KV
to DRAM or SSD and reloads it on demand once the next request
arrives. TokenCake [6] offloads it to DRAM and reloads it into GPU
memory ahead of the agent’s predicted return. Continuum [18]

against reload latency in a different way.

Motivation
To characterize the performance of tiered KV cache offloading in
agentic workloads, we deploy vLLM using the system setup in
Table 1 and the configuration in Table 3 (Section 6.1). We serve the
Qwen3-30B-A3B model on an NVIDIA H100 NVL GPU, which has
32 GiB of GPU memory available for KV caching after accounting
for model weights. We evaluate four benchmarks, DeepResearch
Bench, GAIA, Terminal-Bench 4.0, and BrowseComp-Plus (Table 4),
under increasing system load, varying the number of concurrently
executing agents.

One approach to avoid KV cache restoration is to retain idle
contexts in GPU memory. Continuum [18] follows this approach,
pinning an agent’s KV cache for a time-to-live (TTL) estimated from
tool latencies. While this avoids reloading the context when the
agent returns, it reduces GPU memory available to other requests.
We evaluate this tradeoff further in Section 6.
Observation 3. GPU memory capacity limits the number of concur-
rently executing inference requests, while the aggregate KV cache work-
ing set far exceeds available HBM. Consequently, KV cache restoration
becomes a major source of agent waiting time, limiting how quickly the
GPU can serve new requests.
3.2
L3 Reads in Critical Path
Fig. 6 shows the average distribution of requested KV cache blocks
(per prompt) across cache tiers in our vLLM baseline. Only 2–33% of
tokens are served from GPU memory and 0–28% from host DRAM,
while up to 78% must be retrieved from SSD after request admission.
In addition to the results shown in the figure, we observe that up
to 76% of inference requests stall waiting for SSD reads before
generating their first token. These delays are substantial; retrieving
a 5 GiB context from SSD takes approximately 1–2.5 seconds in
our setup under average load. The numbers above the bars in Fig. 6
report the average time each request spends waiting for its KV
cache blocks to be loaded.
The figure also shows that the fraction of recomputed KV blocks
increases with the number of agents. As concurrency grows, more
requests transfer KV cache data between SSD and GPU, increasing
pressure on host DRAM as well as the interconnect bandwidth. In
vLLM’s inclusive cache hierarchy, DRAM must retain copies of GPU-
resident blocks while also accommodating in-flight transfers to and
from SSD. Under high contention, insufficient DRAM capacity can
prevent some transfers from completing. When a retrieval exceeds
vLLM’s timeout, the engine abandons the transfer and recomputes
the missing KV blocks instead. Consequently, higher load can lead
to more recomputation, even when the required KV blocks remain
available on SSD.
Figure 7: Hits and Misses.
Fig. 7 breaks down KV cache misses by their underlying cause.
For this analysis, we define a cache hit as finding the required KV
block in either HBM or DRAM, and a miss as requiring access
to SSD or recomputation. Following classical cache replacement-
policy studies [12, 29], we compare LRU against Belady’s optimal
replacement policy, MIN [5], and distinguish four types of misses:
• Cold Miss: The required KV block has never been computed.
• Capacity Miss: Even MIN misses when HBM and DRAM are
treated as a single exclusive cache, indicating that their combined
capacity is insufficient.
• Inclusion Miss: MIN hits with an exclusive cache hierarchy but
misses with an inclusive DRAM tier, as duplicate copies reduce
the effective cache capacity.
• Replacement Miss: LRU misses while MIN hits under the same
inclusive hierarchy, indicating a suboptimal eviction decision.
We observe that avoidable inclusion and replacement misses dom-
inate, with their combined percentages shown above each bar in
Fig. 7. To further investigate replacement misses, we measure the
average time an idle KV block remains in the L1 and L2 tiers under
LRU. Fig. 8 shows that tool execution times are typically much
longer than this cache residency time, causing KV blocks to be
evicted before their agents resume inference. As other agents com-
pete for cache capacity during tool execution, LRU evicts the idle
agent’s blocks before they can be reused.

3.3
What, When and Where to Prefetch?
The above findings suggest that retaining every agent’s KV cache
in fast memory is impractical, but retrieving evicted blocks only
after the next inference request arrives is expensive. Instead, we
investigate whether tool execution provides an opportunity to bring
the required KV blocks back before they are needed. This raises
three questions: what, when, and where to prefetch?
Figure 9: Tool Latency (left) and Prediction Error (right).
What to Prefetch? Traditional hardware prefetchers must predict
both what data to fetch and when. For ReAct-style agents, the
first question is largely resolved: an agent’s next inference request
reuses its existing KV cache prefix, which is known in advance.
Only the timing remains uncertain, as reuse follows the completion
of the tool call. This resembles informed prefetching [26], where
applications disclose future data accesses.
When to Prefetch? Fig. 9 (left) shows that tool execution times
provide sufficient time windows for prefetching. Median tool laten-
cies reach up to 10 seconds, while retrieving a 5 GiB context from
SSD at 2–5 GB/s takes approximately 1–2.5 seconds. Accurately pre-
dicting tool completion times is though important, as prefetching
too early wastes cache capacity, while prefetching too late leaves
data retrieval on the inference request’s critical path. Concurrent
work, TokenCake [6], uses moving averages of past tool latencies
to predict completion times. As shown in Fig. 9 (right), fewer than
50% of TokenCake’s predictions fall within ±1 second of actual
completion. However, we find that incorporating tool-specific char-
acteristics, such as tool inputs, and tailoring predictors to individual
tools improves this accuracy to over 90% of calls. We describe these
predictors in Section 5.1. Even imperfect predictions can be useful,
as partial prefetching can reduce the several-second KV-loading
delays observed under high concurrency (Fig. 6).
Where to Prefetch? TokenCake [6] offloads idle KV cache blocks
to host DRAM and prefetches them back into GPU memory ahead
of predicted tool completion. This hides the DRAM-to-GPU transfer
but requires scarce HBM capacity before the request can execute.
With GPU memory accommodating only 5–7 average agent con-
texts, prefetches compete with inference requests for free GPU mem-
ory, increasing queueing delays. We evaluate this effect in Section 6.
Moreover, SSD-to-DRAM transfers are significantly slower than
DRAM-to-GPU transfers (Fig. 2). This suggests that prefetching
into DRAM can hide the dominant transfer cost without reserving
GPU memory in advance.
Observation 5. An agent’s reusable KV cache blocks are known in
advance, and tool completion times can be accurately predicted to de-
termine when they will be needed. Prefetching into DRAM hides the
dominant storage latency without competing with inference requests
for scarce GPU memory.
4
TripleKV Overview
Guided by the observations in Section 2, TripleKV introduces a
KV cache management system that uses prefetching to hide the
latency of data movement across memory tiers. TripleKV builds
on vLLM’s three-level KV cache hierarchy, with GPU HBM, host
DRAM, and SSD serving as L1, L2, and L3, respectively (Observa-
tion 2). It breaks the inclusive property of the L2 tier in vLLM and
makes it a non-inclusive tier to fit more blocks in faster tiers. L3
remains inclusive and every block that is generated in the GPU is
written to it asynchronously. It preserves vLLM’s existing demand
path, where KV blocks are loaded into GPU memory only after re-
quest admission, while extending L2 cache management to support
prefetching. TripleKV introduces three mechanisms:
• Predict: A tool latency predictor in the agent harness estimates
when each tool call will complete and schedules prefetching
ahead of that time.
• Prefetch: A prefetch engine in vLLM asynchronously retrieves
the agent’s KV blocks from L3 into L2.
• Protect: A prefetch-aware cache eviction and replacement policy
retains prefetched blocks until they are reused to avoid premature
eviction.
TripleKV makes two key design choices. First, it never prefetches
into L1, avoiding contention for scarce GPU memory (Observation
3 and 5). Instead, prefetched blocks remain in L2 until the request
is admitted, when vLLM transfers them into L1 over PCIe. This
transfer remains on the critical path but is relatively inexpensive
(≈200 ms). Second, TripleKV does not predict which KV blocks
will be accessed. The agent’s existing context identifies the required
blocks (Observation 1), which are located using the same token-
based hashes as vLLM’s prefix caching. Thus, only the timing of
the prefetch must be predicted (Observation 5).

TripleKV is more efficient than existing agent-aware KV cache

when A’s tool will finish and prefetches A’s KV cache blocks from
SSD into DRAM during the tool call. The SSD read overlaps the tool
call and A’s queueing delay. As a result, after admission, A pays
only the short DRAM-to-GPU load. Since TripleKV neither reserves
nor pins GPU memory, its queuing delays are shorter. Therefore, B
is admitted after a shorter queuing delay.
Protection in L2. TripleKV modifies vLLM’s cache replacement
and eviction policy for the L2 tier to prevent prefetched blocks from
being prematurely evicted (Observation 4). Instead of using naive
LRU, we manage L2 using a multi-queue [43] replacement policy
that uses three queues with different eviction priorities. Prefetched
blocks enter the queue with the lowest eviction priority and stay
protected until their request is admitted to HBM (or until a TTL
expires). We explain this in detail in Section 5.3.
When L2 needs space, the ordinary cached block queue evicts
first, in LRU order. Protected blocks are evicted only when necessary,
starting with those whose protection expires soonest. Protection
ends when a block is reused or its timeout expires, limiting the
impact of inaccurate predictions. To preserve normal cache opera-
tions, protected blocks remain evictable under memory pressure.
Thus, prefetching cannot prevent critical path reads or writes from
completing.
5
Design
TripleKV has three phases: predict, prefetch and protect.
5.1
Predict: When Will the Tool Return?
The tool latency predictor (Fig 11) predicts the time when the tool
call is expected to end. It runs in the agent harness, which sees
each tool call start, its arguments, and its output as it arrives. Like
a branch predictor that keeps a history per branch, it keeps a short
history per tool, including the latencies of that tool’s recently fin-
ished invocations. Prior works [6, 18] also maintain estimates per
tool, but they predict from durations alone. TripleKV’s estimates
also read the call’s input arguments and its live output (if available),
and their form differs between different kinds of tool types. The
top ten most popular tools and their predictors are described in
Table 2. Across all 18.5K tool calls, TripleKV’s predictors have an
MAE (Mean Absolute Error) of 1.1 s versus 7.6 s for TokenCake’s
predictors, and a MAPE (Mean Absolute Percentage Error) of 21%
versus 117%. Fig 9 (right) visualizes this error distribution.

5.2
Prefetch: Moving Data from L3 to L2
The harness sends a prefetch as one API call to vLLM, with the
token IDs of the agent’s context and a timeout. vLLM hashes the
tokens into 64-token block keys exactly as it would for a prompt,
and the prefetch engine walks the blocks in order. The engine runs
inside vLLM’s scheduler loop. Between engine steps, it claims the
blocks already in L2, and then performs lookups and reads in L3
which go through the same path that serves requests, at prefetch
priority. A prefetch stops at the first block missing from every tier,
since the request must recompute everything after it anyway.
Every L3 access goes through one of the three FIFO queues as
shown in Fig 12. The miss queue holds reads that are in the critical
path of a waiting request. The prefetch queue holds prefetch and
refill reads. A refill also fetches a block from L3 into L2. It is issued
when L1 evicts a watched block. When a block to be prefetched is
Figure 12: Read and Write Queues between L2 and L3.
Figure 13: KV Cache Block State Diagram.
found to be in L1, TripleKV adds its hash to a watch list instead
of prefetching it into L2, to avoid redundancy. If the block in L1 is
evicted before the request can use it, the watch list adds it to the
prefetch queue as a refill read so that it can be loaded into L2. This
mechanism behaves like a victim cache [13].
The store queue holds the write-through stores of new blocks.
Each 6 MiB block is one data movement task, so the reads of one
context spread over many threads. Two groups of threads drain the
queues in different orders. The read-priority threads take misses
first, then prefetches, then stores, so no thread starts a prefetch
read while a miss is waiting. The write-priority threads take stores
first, then misses, then prefetches, so the write-through keeps mov-
ing under heavy read load and neither direction starves. When a
request arrives while its own prefetch is still queued, those tasks
are promoted to the miss queue and are read as misses.
5.3
Protect: Eviction and Replacement for L2
A prefetch helps only if its blocks are still in L2 when the request
arrives. In order to ensure this, TripleKV uses a prefetch-aware
cache eviction and replacement policy for L2. This is inspired from
a multi-queue replacement policy [43] that uses three queues with
different eviction priorities.
Each L2 block lives in one of the following three classes (and
their corresponding LRU queues). Fig 13 shows the state diagram.
• PREFETCHED: A prefetched block that L1 does not hold.
• BACKUP: An L2 copy of a block that L1 still holds.
• CACHED: All other blocks.
7


Jaiswal et al.
The eviction priority is CACHED > BACKUP > PREFETCHED.
Within each queue, LRU is followed with entering the queue count-
ing as a use. This is done to ensure that PREFETCHED blocks
are evicted as the oldest prefetched first (same for BACKUP). A
BACKUP is promoted to a PREFETCHED block when L1 evicts its
copy, because L2 then holds the only fast copy.
Protection ends in one of two ways, either when a request uses
the block or when its timeout expires unused (120s in our runs). In
either case, it joins the CACHED queue.
Protection is considered a priority, but the blocks are not pinned.
If a demand read or a store finds no unprotected block to evict, it
evicts a protected one. A wrong or excessive prefetch therefore
degrades L2 toward basic LRU instead of blocking demand traffic.
Moreover, a small amount of reserve space (256 blocks or 1.5 GiB
in our runs) is kept free on the L2 for blocks in flight between tiers.
5.3.1
Refill: Watching Blocks Still in L1. When a prefetch is issued,
part of the agent’s context may still be in L1. In our experiments,
we see that up to 30% of prompt tokens may be resident in L1 when
the corresponding prefetch is issued. Those blocks are useful only
while L1 keeps them, and L1 may evict them to admit other requests
before this agent uses them. TripleKV introduces a watch list to
solve this problem (Fig 12). Each block of the prefix that is in L1 but
not in L2 is added to a watch list. When a watched block is evicted
and no other GPU block holds the same content, TripleKV reads it
from L3 into a protected L2 slot. A watch ends either when (1) the
request uses the block in L1, (2) the L1 block is evicted and refill
is issued, or (3) the TTL expires. This behaves like a victim cache
mechanism [13].
5.4
Implementation and Overheads
TripleKV extends vLLM’s offloading connector, which already puts
a CPU tier and may be configured to put a file-system tier behind
the GPU as write-through storage. We add protection classes to
the CPU tier, the prefetch engine and watch list to the tier man-
ager, the three-queue thread pool to the file-system tier, and a
/kv_cache/prefetch endpoint to the server. This is about 3000
lines of code. The predictor is implemented in the agentic harness.
It is under 300 lines of Python code, and issues one prefetch call
per tool call. Our runs use 64-token offload blocks (6 MiB) and 64
GiB of L2 per GPU (about 10,900 blocks) with a 120s timeout.
TripleKV’s costs fall outside the critical path. It reserves no GPU
memory and adds no GPU work, since blocks reach L1 through
vLLM’s existing loads from L2. A prefetch call is asynchronous and
its reads have lower priority than block reads on the critical path
of requests. The bookkeeping is a few table entries per protected
or watched block that adds up to a few thousand entries at most in
total.

Cache Metrics
We evaluate TripleKV’s prefetching with standard cache metrics
like coverage, precision and timeliness.
Figure 19: Cache Coverage.
Cache Coverage. We define cache coverage as the share of the KV
cache data a request loads from below L1 that it finds in DRAM (L2),
thereby avoiding reads from SSD (L3) at admission. Fig 19 shows
that TripleKV’s coverage is 96–100% at every point except GAIA 20
(87%) and BC+ 20 (60%). This is because, at these two points, the
contexts TripleKV protects outgrow the available DRAM capacity.
Prefetched blocks are then evicted before their request arrives, 13%
of them on GAIA 20 and 38% on BC+ 20, and the request reads them
again from SSD at admission. Below capacity, almost no prefetched
block is lost, and coverage stays near 100%. For comparison, vLLM
with L3 finds only 5–39% of this KV in DRAM.

moved from SSD to DRAM that its request needed. TripleKV’s
precision is 97–100% at every point, including the two points where
coverage dropped. This is shown in Fig 20.

Related Work
Agent-aware KV management. Systems handle an idle agent’s KV
in three ways. (1) Prefetching: TokenCake [6] reloads stalled agents
from DRAM into HBM before predicted completion. Its predictions
are based on a moving average of the tool latency and developer
hints. KVFlow [25], PBKV [41] and CacheScout [40] prefetch the
context of the agents that is predicted to run next, without consid-
ering when it will run. (2) Retention: Continuum [18] pins KV in
HBM for a time-to-live determined by reload and queueing costs.
InferCept [1] keeps, swaps or recomputes paused requests’ KV
to minimize idle memory waste, and MORI [34] keeps only busy
agents in HBM based on their recent idleness. (3) Application cues:
SYMPHONY [2] and Nalar [3] act on application hints and Ask-the-
Tool [20] on tool-reported progress to perform KV cache movement
between DRAM and GPU. These require reprogramming the appli-
cation or its tools, which is a significant overhead. TripleKV adds a
predictor only to the agent harness and works with existing tools or
the application. It prefetches KV cache blocks into the host DRAM
and protects prefetched blocks to prevent premature eviction.
Hierarchical KV caching. CachedAttention [11] and Strata [36]
fetch KV from disk into DRAM after the requests have been queued,
and CachedAttention exempts its look-ahead window from evic-
tion. LMCache [19], Mooncake [27], SGLang [42], HiCache [35]
and Dynamo KVBM [24] extend the cache to storage. HiCache
fetches into host memory after the request is known once its prefix
match passes a threshold. Pensieve [38] swaps multi-turn chat state
between GPU and CPU ahead of time. DualPath [33] finds agen-
tic inference storage-bound and proposes reading the KV cache
through two network paths instead of one. These system start read-
ing once the request is known. TripleKV reads the offloaded KV
11


Jaiswal et al.
cache before the agent resumes and hides the read latency during
the tool execution phase.
Informed prefetching and integrated caching. TIP [26] prefetches
from disclosed future accesses and bounds how far ahead to issue
them. The Aggressive and Conservative policies [7] set rules for
when to prefetch and what to evict. Reverse Aggressive [14] extends
them to parallel disks, and LP-based schedules [4] minimize stall
time optimally. TripleKV’s prefetching is a deadline form of TIP’s
horizon, with a tool predictor in place of disclosure.
Prefetch-aware replacement and exclusive hierarchies. TripleKV’s
Protect follows prefetch-aware replacement in CPU caches [32, 43]
and GPU unified memory [10]; like MIN-based policies [5, 12, 29].
It uses knowledge of future reuse. The watch list resembles victim
caching [13] and DEMOTE-style exclusive caching [31], but it refills
evicted blocks from the lower tier instead of capturing them on
eviction, to avoid stalling the GPU on each eviction.
8
Conclusion
This paper presented TripleKV, a novel agent-aware KV cache man-
agement framework. TripleKV predicts when each tool will finish,
prefetches the agent’s KV blocks from SSD into DRAM before the
next request, and protects them there until they are used. Across
four agentic benchmarks, TripleKV reduces the fraction of requests
requiring critical-path SSD reads from 45–76% to under 10%. It also
reduces P95 TTFT by up to 49% compared with vLLM extended
with DRAM and SSD KV-cache tiers, and achieves 1.5-7× lower P95
TTFT than recent agent-aware systems.
