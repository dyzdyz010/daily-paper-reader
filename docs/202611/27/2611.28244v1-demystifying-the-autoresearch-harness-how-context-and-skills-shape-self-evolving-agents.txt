Abstract | Autoresearch agents, which autonomously design, run, and refine experiments, are accelerating
scientific progress, particularly in AI research. However, existing agents rely on harnesses that combine multiple
mechanisms, making it difficult to determine how individual components contribute to performance. We
systematically study harness design for long-horizon, self-evolving autoresearch agents along two dimensions:
context management, which determines what an agent retains from its past attempts, and skill management,
which governs how it stores and reuses lessons from those attempts. Across MLE-Bench and KernelBench with
gpt-oss-120b, gpt-6-luna, and gpt-6-sol, we isolate the effects of individual harness design choices
by evaluating each against a recency-truncation baseline within a shared agent framework. For context
management, we find that preserving individually accessible records of past attempts is more effective than
maintaining a rolling summary, with context folding performing best across all six settings and improving upon
the baseline by up to 19.2%. For skill management, selectively discarding persistently unused lessons is more
effective on average than consolidating them or promoting them to standing rules. Building on these findings,
we combine context folding and skill deletion in MLEvolver, which achieves a 72.7% medal rate on MLE-Bench
Lite and a 94% fast1 score on KernelBench Level 3, substantially outperforming AIDE and OpenEvolve under
the same inference budget. Overall, our study distills design principles for preserving experimental history
and curating reusable lessons in autoresearch harnesses, paving the way for agents that turn accumulated
experience into sustained progress.
1. Introduction
Autoresearch agents can automate the cycle at the heart of empirical research: given a task and a
grader, they propose an idea, implement it, run the experiment, read the result, and decide what to
try next. They are becoming increasingly important in AI for AI (AI4AI), where improving existing
AI systems directly accelerates subsequent research. Recent autoresearch agents demonstrate this
across diverse domains: on MLE-Bench [Chan et al., 2025], AIDE [Jiang et al., 2025], and ML-Master
[Liu et al., 2025b] iteratively train and tune competitive machine learning pipelines. On KernelBench
[Ouyang et al., 2025], Kevin [Baronio et al., 2026] learns to write and iteratively refine fast CUDA
kernels, and AlphaEvolve [Novikov et al., 2025] has even sped up the training of the language models
it is built on. What is common among these workflows is their long horizons operation. The agent
attempts the same task tens or hundreds of times, receives an evaluation score after each attempt,
and iteratively refines its solution.
Over such horizons, an agent’s behavior depends not only on its language model, but also on the
harness that manages the memory it accumulates about its own past. This memory takes two forms,
each under a different kind of pressure. The first is the history of past attempts. It grows with every
attempt, and soon exceeds the context window, thereby leading to truncation [Packer et al., 2023].

The second is a library of skills: natural language lessons distilled from earlier attempts and retrieved
when a similar situation recurs [Shinn et al., 2023, Zhao et al., 2024]. The library can grow without
limit, but it can become redundant and noisy, which makes the right lessons harder to retrieve. What
an agent keeps, condenses, or discards in each form of memory is therefore a central design decision.
Many mechanisms have been proposed for managing this memory. Agents page information in and
out of context [Packer et al., 2023], reflect on and summarize past experience [Park et al., 2023, Shinn
et al., 2023], and extract, revise, and reuse insights or workflows [Zhao et al., 2024]. However, these
mechanisms are typically evaluated within multi-component systems where differences in search
policies, prompt structure, and tool use confound cross-system comparisons. Even when individual
studies ablate their own designs, memory mechanisms are rarely evaluated head-to-head under a
shared, unified harness. As a result, it remains unclear what each mechanism contributes on its own.
We address these questions through a controlled, bottom-up study of memory harness design in
iterative self-improvement, where an autoresearch agent repeatedly attempts the same task and
receives empirical feedback after each attempt. This setting strains both memory tiers early: the
execution history quickly overflows the context window, while the skill library accumulates redundant
lessons. Starting from a minimal recency-truncation baseline, we isolate five memory mechanisms
within an otherwise identical agent by changing exactly one component at a time (Figure 2). Two
manage working context: folding condenses each attempt into an expandable digest, and compaction
aggregates older history into a running summary. Three govern the skill library: deletion prunes
unused lessons, merging consolidates semantic duplicates, and promotion elevates proven skills into
persistent standing rules.

For context management, folding achieves the highest performance among all evaluated mechanisms
in all six model–benchmark settings, improving MLE-Bench GNS by up to 7.9% and KernelBench
geometric-mean speedup by up to 19.2% over recency truncation. Our context analysis links this
advantage to folding’s preservation of a separate digest for every attempt, which exposes more of the
agent’s history within the context budget. Compaction compresses older attempts into a single rolling
summary, leaving progressively less detail about each experiment as the history grows. Folding keeps
individual attempts accessible throughout the run, helping the agent draw on earlier successes and
failures when choosing its next experiment.
For skill management, deletion yields the largest average improvement at 4.1% over the recency-
truncation baseline. These results favor the removal of persistently unused lessons over merging
similar skills or promoting them to standing rules. Our skill analysis also reveals consistent differences
in retrieval behavior across the three backbones. Across configurations, gpt-oss-120b selects 6.4–
7.1 skills per attempt, compared with 1.2–1.9 for gpt-6-luna and 0.5–0.6 for gpt-6-sol. This
ordering persists across the baseline and all three skill-management mechanisms, indicating that the
backbone strongly influences how much stored experience enters each attempt.
Guided by these findings, we build MLEvolver by combining context folding and skill deletion, the
best-performing mechanisms on average in their respective dimensions. We compare MLEvolver
with AIDE and OpenEvolve using gpt-6-sol and a shared cap of 100 iterations per run. As shown

• A controlled study of harness design for long-horizon, self-evolving autoresearch agents: six
configurations within one agent that isolate five context- and skill-management mechanisms
against a recency-truncation baseline.
• An evaluation across three model backbones and two AI4AI benchmarks, with analyses of the

2. Related Work
Harness Design and Memory in Autoresearch. Autoresearch harnesses orchestrate iterative discov-
ery by structuring how language models store, retrieve, and build upon past attempts. Existing systems
couple search logic with bespoke memory stores: FunSearch [Romera-Paredes et al., 2024] and
AlphaEvolve [Novikov et al., 2025] maintain program databases, AIDE [Jiang et al., 2025] manages
candidate trees, and ML-Master [Liu et al., 2025b] integrates a selectively scoped execution log into
its harness. Broader agent harnesses also develop targeted mechanisms to mitigate context bounds.
These harnesses page state in and out of prompt buffers [Packer et al., 2023], summarize completed
sub-goals [Hu et al., 2025], train models to fold execution trajectories [Sun et al., 2026, Ye et al.,
2026], or mask older observations to match summarization at reduced token cost [Lindenbauer et al.,
2025]. For procedural skills, prior frameworks accumulate verbal reflections [Shinn et al., 2023],
distilled insights [Zhao et al., 2024], or synthesized experience replays [Liu et al., 2025a]. However,
uncurated skill catalogs degrade retrieval accuracy as they expand [Li, 2026]. Recent harnesses
address this bloat through heuristic forgetting [Zhong et al., 2024], pruning low-utility records [Xiong
et al., 2026], or injecting curated operational playbooks into working context [Chen et al., 2024,
Zhang et al., 2026]. Unlike prior frameworks designed for single trajectories, cross-task transfer, or
brief retries, autoresearch harnesses must sustain refinement across long horizons of scored attempts.
In our study, we compare five context- and skill-management mechanisms within a shared harness,
varying one component at a time.
AI4AI Benchmarks. A growing set of benchmarks employs agents to automate the development of
AI systems themselves, a direction that ML-Master [Liu et al., 2025b], MLAgentBench [Huang et al.,
2024] and MLE-Bench [Chan et al., 2025] task agents with improving machine learning models on
research problems and Kaggle competitions. KernelBench [Ouyang et al., 2025] and TritonBench
[Li et al., 2025] focus on writing correct and fast GPU kernels. On RE-Bench [Wijk et al., 2025],
agents outperform human experts under short time budgets but gain less from longer ones, so the
effectiveness of making use of a long run of attempts remains an open problem for autoresearch
agents. We use MLE-Bench and KernelBench, where every attempt is scored, so each mechanism’s
effect can be tracked throughout a run.

3. Memory Mechanisms
In this section, we introduce the iterative self-evolution procedure and detail the memory mechanisms
across two aspects: context management (§3.3) and skill management (§3.4). Figure 2 illustrates
one iteration and how each memory mechanism interacts with the agent.
3.1. The Iterative Self-Evolution Loop
Each task is solved through a sequence of scored evolution iterations. At iteration 𝑡, the agent
first selects an action from three operators: propose_new, which develops a new approach;
refine_current, which modifies the incumbent solution; and debug_current, which addresses
a failure in the incumbent. A skill picker then selects reusable skills from the task-specific skill library.
The coder receives the task, standing rules, selected skills, and the representation of the previous
attempt history, and produces the next solution. The benchmark evaluator executes the solution and
returns task-specific feedback. Finally, a skill writer records lessons from the iteration. Skill creation
remains an agent decision and any iteration can request zero or more skills.

4. Experiments
4.1. Experimental Setup
We evaluate the five memory mechanisms and baseline on two machine learning benchmarks.
MLE-Bench evaluates agents on Kaggle machine-learning competitions [Chan et al., 2025], while
KernelBench evaluates agents’ ability to generate fast and correct GPU kernels for machine-learning
workloads [Ouyang et al., 2025].
We use three model backbones, gpt-oss-120b [OpenAI
et al., 2025], gpt-6-luna [OpenAI, 2026a] and gpt-6-sol [OpenAI, 2026b]. For merging,
Qwen3-Embedding-0.6B [Zhang et al., 2025] is used to generate the skill embeddings.
Each task has an independent skill library, which is reset before the task begins. All configurations for
a given task start from the same seed solution that is curated to be deliberately weak. The memory
policy determines how the attempt history and skill information occupy the context.
MLE-Bench. We evaluate on 10 competitions from MLE-Bench [Chan et al., 2025], comprising six
low-complexity and four medium-complexity competitions. The selected competitions and benchmark-
specific modifications are detailed in Appendix B.
Each configuration runs 100 iterations per competition. In each iteration, the agent’s solution trains
on the competition’s training data and writes a submission, which is then graded. The agent then
receives its score under the competition’s metric, together with any terminal output produced during
execution. Because the metrics differ in scale and direction, we report a gold-normalized score (GNS),
analogous to the human-normalized score in reinforcement learning [Mnih et al., 2015]:

KernelBench. We evaluate 50 KernelBench problems across three difficulty levels [Ouyang et al.,
2025]: 20 Level-1 individual operators, 20 Level-2 fused operator chains, and 10 Level-3 model

Each configuration runs for 50 refinement iterations per problem. At each iteration, the generated

4.2. Main Results
Folding performs best across all model backbones and both benchmarks. Table 1 reports results
across 10 MLE-Bench competitions and 50 KernelBench tasks. Folding achieves the highest perfor-
mance among all evaluated mechanisms in all six settings, with an average relative improvement of
8.6% over the baseline. Its gains range from 1.6% to 7.9% on MLE-Bench and 8.3% to 19.2% on Ker-
nelBench. With gpt-oss-120b, folding raises GNS from 70.5 to 76.1 and geometric-mean speedup
from 1.17× to 1.29×. With gpt-6-sol, it raises GNS from 93.2 to 94.7 and geometric-mean speedup
from 2.16× to 2.34×. These improvements span the lowest- and highest-performing backbones in our
study. The context analysis in Section 5.1 examines how retaining individually accessible records of
earlier attempts contributes to this consistent advantage.
Skill management consistently improves performance, with deletion performing best on average.
Deletion, merging, and promotion improve on the baseline for all models and benchmarks. Deletion
yields the largest average relative gain at 4.1%, followed by promotion at 3.0% and merging at 2.2%.
Averaged across the three mechanisms and both benchmarks, the gains are 5.1% for gpt-oss-120b,
1.9% for gpt-6-luna, and 2.1% for gpt-6-sol. Compared with gpt-oss-120b, gpt-6-luna
gains 3.2 percentage points less on each benchmark. For gpt-6-sol, the gap is 3.5 points on
MLE-Bench and 2.5 points on KernelBench. Section 5.3 analyzes this difference by investigating how
the three models interact with the skill library.

5.3. Model Differences in Skill Retrieval and Orientation
The different gains from skill management coincide with differences in how the three model backbones
use the skill library. Figure 4b shows that gpt-oss-120b retrieves 6.4–7.1 skills per prompt across
configurations, whereas gpt-6-luna retrieves 1.2–1.9 and gpt-6-sol retrieves 0.5–0.6. This
ordering holds across the baseline and all three skill-management mechanisms, suggesting consistent
differences in the models’ skill selection behavior.
The models also differ in the orientation of the knowledge drawn from the skill library. We classify a
skill as offensive when it encourages a new implementation, optimization, or search direction intended

to improve the score, and as defensive when it primarily protects the current solution by preserving
correctness or avoiding known failures. Full classification criteria are provided in Appendix E.1. As
shown in Figure 4c, 53.1% of the skills retrieved by gpt-oss-120b are offensive, compared with
30.2% for gpt-6-luna and 25.4% for gpt-6-sol.
Together, these observations suggest that the two proprietary backbones, gpt-6-luna and
gpt-6-sol, use the skill library more conservatively. They draw on fewer stored experiences and
more often select knowledge aimed at protecting existing performance. The open-weight backbone,
gpt-oss-120b, draws on a broader set of experiences with a more even balance between protective
guidance and active optimization. This difference offers one explanation for why skill management
provides larger gains for gpt-oss-120b.

Harnesses. MLEvolver combines the best-performing mechanism on average in each dimension:
folding for context management and deletion for skill management. AIDE [Jiang et al., 2025] searches

a tree of candidate solutions. At each step, it drafts a new solution, refines the best node found

Benchmarks and budget. We evaluate 22 competitions in MLE-Bench Lite, the low-complexity split

6.2. Results
MLEvolver outperforms AIDE and OpenEvolve on both benchmarks. As illustrated in Figure 5a
and Figure 5b, MLEvolver earns medals in 16 of 22 MLE-Bench Lite competitions (72.7%), a relative
gain of 23.1% over AIDE and 14.3% over OpenEvolve. It wins 10 gold medals, 42.9% more than
either baseline. On KernelBench Level 3, MLEvolver reaches 94% on fast1, a relative gain of 20.5%
over AIDE and 34.3% over OpenEvolve. At the stricter fast2 threshold, MLEvolver produces correct
kernels with more than 2× speedup over PyTorch Eager on 31 of 50 problems (62%), more than
twice as many as AIDE and more than four times as many as OpenEvolve. These results show that
MLEvolver is effective for long-horizon, self-evolving autoresearch on machine learning tasks.
MLEvolver pulls ahead early and extends its lead. Figure 5c and Figure 5d show that MLEvolver
reaches 97.4 GNS by iteration 20 on MLE-Bench Lite and a 2.08× geometric-mean speedup by iteration
10 on KernelBench Level 3. On both benchmarks, these early results exceed the performance that AIDE
and OpenEvolve reach at iteration 100. On MLE-Bench Lite, MLEvolver maintains its lead and finishes
at 98.1 GNS, 1.4% higher than AIDE and 2.6% higher than OpenEvolve. On KernelBench, MLEvolver
widens its lead in the second half of the run. Between iterations 50 and 100, its geometric-mean
speedup increases by 11.9%, from 2.67× to 2.99×, while AIDE and OpenEvolve improve by 0.8% and
5.2%, respectively.
6.3. Discussion
Folded history supports informed exploration and refinement. All three systems can explore
different approaches. AIDE [Jiang et al., 2025] follows a predefined policy for drafting, debugging,
and improving solutions, with hyperparameters controlling the number of initial drafts and debugging
behavior. OpenEvolve [Sharma, 2025] samples parent and inspiration programs from its populations
according to configured rules. In MLEvolver, the model uses a catalog of attempt digests to decide
whether to refine a promising solution, debug a failure, or propose a new approach when progress
stalls. It can also retrieve full records of relevant earlier attempts, including their code, recorded
reasoning, scores, and execution output. This combination provides an overview of previously explored
directions and access to the details needed to build on earlier successes and failures. The value of
retaining this access is reflected in Section 5.1, where folding preserves more experimental history
within the context window and achieves a higher new-best rate during later iterations.

Distilled skills give MLEvolver direct guidance for later attempts. AIDE summarizes earlier valid
solutions, and OpenEvolve provides selected programs alongside summaries of recent changes, metrics,
and outcomes. Alongside the attempt digests, MLEvolver maintains a separate library of lessons
distilled from its experiments. Retrieving these lessons directly reduces the need to reconstruct
them from earlier code and results. Offensive skills suggest promising directions to explore, while
defensive skills record constraints and failure patterns that can help the model avoid repeating
mistakes. Deletion prunes persistently unselected skills, using the model’s retrieval behavior as a
signal of which lessons remain relevant as the search progresses. The benefits of both retaining and
managing these lessons are supported by Section 5.2, where maintaining the skill library improves
performance and deletion provides a further gain.
Solution space shapes scaling. The two benchmarks differ in the structure of their solution spaces.
On MLE-Bench Lite, the solution space is more discrete, with promising solutions built around
distinct choices of model family and feature representation. The harnesses can therefore start with
substantially different submissions, contributing to the spread in GNS at iteration 1. On KernelBench,
the solution space is more continuous. The first correct kernels run about as fast as PyTorch Eager on
average, and later optimizations yield incremental speedups. These differences favor different search
strategies. On MLE-Bench Lite, exploring several distinct candidates increases the chance of finding a
strong solution. AIDE explores candidates across branches of a search tree, and OpenEvolve samples
from a population of programs. As the runs progress, AIDE’s gap to MLEvolver narrows from 3.5%
to 1.4%, and OpenEvolve’s narrows from 15.4% to 2.6%. On KernelBench, successive optimizations
can build on one another, favoring sequential self-refinement. MLEvolver uses a single refinement
chain with context folding and skill deletion, so each new edit can draw on results and lessons from
earlier attempts. AIDE refines a node in its search tree, and OpenEvolve edits a sampled parent
with guidance from selected programs. In both cases, the model has a more limited view of which
optimizations succeeded or failed in earlier attempts. Between iterations 50 and 100, MLEvolver
increases its geometric-mean speedup from 2.67× to 2.99×, while AIDE and OpenEvolve make smaller
gains and finish at 1.85× and 1.41×, respectively.
7. Conclusion
We present a controlled study of harness design for long-horizon, self-evolving autoresearch agents.
Within one agent, we isolate five memory mechanisms and compare each with a recency-truncation
baseline on MLE-Bench and KernelBench using gpt-oss-120b, gpt-6-luna, and gpt-6-sol.
Three findings emerge from the experiment. First, folding performs best in all settings by condensing
each attempt into a short digest, allowing the agent to retain more experimental history within the con-
text budget and target solutions more effectively. Second, both retaining skills and actively managing
them improve performance, with deletion providing the largest average gain among skill-management
mechanisms. Third, the benefits of skill management vary with the model backbone’s skill selection
behavior. Both gpt-6-luna and gpt-6-sol retrieve fewer skills and favor defensive guidance more
strongly than gpt-oss-120b, accompanying their smaller gains from skill management. Based on
these findings, we combine folding and deletion in MLEvolver, which achieves a 72.7% medal rate
on MLE-Bench Lite and 94% on fast1 on KernelBench Level 3, outperforming AIDE and OpenEvolve
on both benchmarks. Overall, our study identifies effective choices for preserving experimental
history and curating reusable lessons, providing an empirically grounded foundation for long-horizon,
self-evolving AI research agents.

Limitations
Our study isolates memory mechanisms within linear, sequential refinement loops and leaves parallel
scaling unexplored. Parallel search strategies, such as concurrent tree search and population-based
evolution, distribute attempts across parallel trajectories and place distinct demands on context
budgets and skill selection. Our system comparisons cover structured autoresearch frameworks with
guided research loops. Interactive coding agents, such as Claude Code or Codex, are not evaluated.
They execute open-ended sequences of tool calls and internal refinement rounds, making it difficult
to define a common unit of iteration or enforce comparable evaluation budgets across systems. Finally,
each task initializes an independent skill library. Our findings therefore characterize within-task
experience accumulation, leaving other evolutionary effects, such as cross-domain skill transfer and
multi-task skill distillation, for future work.

A. KernelBench Protocol and Evaluation Details
We evaluate all agent configurations on 50 tasks from KernelBench [Ouyang et al., 2025]. This section
describes the evaluation environment, timing procedure, task subset selection, and reward-hacking
safeguards.
A.1. Evaluation Environment and Timing Protocol
All evaluations execute on a dedicated NVIDIA GH200 144G HBM3e GPU. The software environment
runs Python 3.10.20, PyTorch 2.11.0+cu128, and CUDA 12.8.
Equivalence Verification. Following Ouyang et al. [2025], functional correctness evaluates numerical
output equivalence between the PyTorch reference implementation and the agent’s submitted kernel
on identical input tensors.
Latency Measurement. The original KernelBench protocol [Ouyang et al., 2025] uses the arithmetic
mean execution time across runs to compute speedup, as its benchmark suite exhibits a coefficient
of variation (𝜎/𝜇) below 3%. In our long-horizon agent setting, execution times do not consistently
remain within this variation threshold across repeated compilation and execution passes. We therefore
use the median execution time to compute speedup, reducing the influence of transient operating-
system overhead and driver allocation spikes.
A.2. Stratified Problem Selection
KernelBench contains 250 problems across three difficulty levels. The full suite includes many
similar operations evaluated with different tensor shapes, so uniform sampling could overrepresent
some computational patterns. We therefore construct a 50-task subset from 28 strata defined by
computational structure. The subset includes at least one task from every stratum and preserves
the benchmark’s 2:2:1 level distribution: 20 Level-1 tasks testing individual operators, 20 Level-2
tasks testing fused operator chains, and 10 Level-3 tasks testing model architectures. Table 2 lists the
selected problems and their stratum assignments.
Sampling Frame and Exclusions. Our sampling frame contains 238 of the 250 KernelBench problems:
99 from Level 1, 89 from Level 2, and all 50 from Level 3. We exclude 12 problems for the following
reasons:
• Degenerate problems (3 Level-2 tasks: p23, p80, and p83). The reference implementations
produce outputs that are either identically zero or numerically indistinguishable from zero under
the benchmark’s correctness tolerance. For example, in problem 80, a column-wise maximum
reduces the tensor to a single column, after which mean subtraction and GELU produce an
all-zero output. A trivial kernel that returns zeros can therefore pass numerical validation
without performing the intended computation. We exclude these problems because they do not
meaningfully evaluate kernel optimization.
• Algebraically reducible problems (8 Level-2 tasks: p13, p14, p18, p42, p44, p51, p65,
and p98). In these problems, a matrix multiplication or convolution is followed by operations
that permit most of the original computation to be removed through algebraic simplification.

objective that combines the Kolmogorov–Smirnov (KS) distance, the difference in mean log runtime,
and deviation from the target level distribution. Reference runtime is the median latency of the
PyTorch eager implementation on the evaluation hardware and is independent of agent performance.
A.3. Anti-Reward-Hacking Safeguards
Kernel-generation agents can discover shortcuts that increase measured speedup without implementing
the intended computation [Baronio et al., 2026, Dai et al., 2026]. We combine static code inspection,
runtime isolation, and prompt-based guidance to detect or discourage these strategies.
Reference Output Isolation. Prior work has shown that candidate kernels may exploit outputs left in
GPU memory by the preceding reference execution [Baronio et al., 2026]. In particular, a candidate
that allocates an uninitialized tensor may receive memory containing values from the reference output
and pass numerical verification without writing every output element. We prevent this shortcut by
retaining the reference output until numerical verification is complete, so its device memory cannot
be reused during candidate execution.
Static Code Inspection. Before compilation, we inspect each candidate implementation using Python’s
ast module. The validation gate rejects candidates that:
1. do not define explicit CUDA source containing at least one __global__ kernel;
2. delegate all reference operations to high-level frameworks or compilation interfaces instead of
implementing a complete operation in a custom kernel;
3. patch timing functions, reference modules, or evaluation code;
4. modify input tensors or tensor references in place; or
5. spawn background threads or processes, or defer timed work to an execution stream that is not
synchronized with the primary stream.
A candidate that fails any of these checks is marked invalid and can never become the task’s best
attempt; speedup is computed from each task’s best valid attempt.
Numerical State Isolation. Candidates also attempt to alter the evaluation by changing process-wide
numerical settings, such as PyTorch matrix-multiplication precision or global TF32 flags. The harness
records the relevant numerical settings and restores the required evaluation configuration before
reference timing. Candidates that modify prohibited precision or backend settings are rejected. This

prevents a candidate from obtaining an apparent speedup by reducing numerical precision or by
slowing the reference implementation.
Prompt-Based Integrity Guidance. The runtime safeguards are complemented by prompt instruc-
tions that discourage invalid optimization strategies before code is generated or reusable knowledge is
recorded. These instructions guide the agent toward genuine kernel optimization but are not treated
as enforcement mechanisms.
KernelBench Integrity Rules
1. Compute the intended operation. At least one custom CUDA kernel must implement a complete
operation or fused group from the reference model. Dummy kernels, identity operations, and staging
copies do not qualify.
2. Preserve correctness beyond observed inputs. Implementations may specialize to the declared
shapes, dtypes, constructor arguments, and target GPU, but not to particular input values, weights,
memory addresses, call counts, or random seeds.
3. Use only exact simplifications. Algebraic rewrites are allowed when they preserve the reference
computation for every valid input and weight. Approximations and shortcuts that hold only for
observed test inputs are not allowed.
4. Preserve the required numerical precision. Implementations may not introduce lower-precision
arithmetic, approximate mathematical operations, or prohibited changes to process-wide precision
settings.
5. Do not manipulate evaluation. Implementations may not modify inputs, reference buffers, timers,
backend settings, execution streams, threads, or processes to influence correctness or latency mea-
surements.

E. Behavior Data on Each Design
E.1. Offensive and Defensive Skills
To describe the skill each backbone chooses, we label all of them as offensive or defensive by their main
purpose. An offensive skill aims to raise the score of a working solution: a modeling technique, feature,
ensemble, or tuning step on MLE-Bench; a kernel technique such as fusion, tiling, shared-memory
reuse, or vectorized access on KernelBench.
A defensive skill aims to prevent failure or loss. Its main responsibility is to avoid crashes, version
errors, time or memory overruns, guard against leakage and overfit, or against incorrect results,
imprecise numerics, and timing noise on KernelBench.
Rules. A skill is read as its title, description, and applicability trigger. The title is lower-cased and its
qualifiers are removed. Seven fixed rules are tried in order, and the first that matches decides, so no
model is involved. Because the title states the skill’s main action, rules 1–6 read only the title:
1. Defensive verb (defensive): the title starts with a protective verb, such as preserve, protect, keep,
validate, guard, gate, avoid, prevent, bound, correct, fix, detect, or diagnose
2. Caution (defensive): a warning word or phrase appears anywhere in the title, such as “not”,

E.3.1. Merging Can Remove Task-Specific Details
KernelBench Level 1, Problem 3 — Dense Batched Matrix Multiplication
Before merging
Skill 9. Consider a tensor-core implementation only if it preserves the required FP32 semantics. Do not
substitute TF32, FP16, or BF16 when FP32 is required. No tensor-core implementation was tested.
Skill 10. Address the scalar-FMA bottleneck while preserving FP32 semantics. Retain boundary masks
unless divisibility is guaranteed.
After merging
Use a tensor-core implementation that meets the required PRECISION contract. Use lower
precision only when the contract permits it. Retain masks unless divisibility is guaranteed.
At iteration 10 of this run, merging replaces the explicit FP32 requirement with an unfilled placeholder
and omits that the tensor-core approach was untested.
MLE-Bench — Denoising Dirty Documents
Before merging (source skill 13)
When editing nested extend or append calls containing NumPy expressions, check for a missing closing
parenthesis. In this case, the nested wide_maps.extend(...) expression needs one more closing
parenthesis.
After merging (skill 11)
Balance delimiters from the innermost expression outward and run a syntax check before starting
costly processing.
In this run, skill 11 absorbed skills 13–15 in three successive merges. The final merged skill retains
the general syntax advice but omits the specific expression recorded in skill 13. The same missing-
parenthesis error recurs at iteration 79. At iteration 80, the debugging attempt retrieves only the
merged skill 11, leaves the faulty expression unchanged, and fails with the same syntax error.
E.3.2. Promoted Rules Can Outlast Their Applicability
KernelBench Level 2, Problem 57 — Convolution with ReLU and HardSwish
Promoted rule
When fusing ReLU and HardSwish in one hand-written CUDA kernel, preserve FP32 evaluation order and
remove only the lower clamp made redundant by ReLU.
Later in the run
By iteration 20, cuDNN handles ReLU and the separate CUDA kernel computes HardSwish only.
At iterations 30 and 50, the incumbent again fuses both activations in a hand-written convolution.

System Prompt: Standing-Rule Promotion
You are an L2 standing-rule promoter.
L1 skills are lessons distilled from this task’s earlier attempts. Most are situational: the
retrieval step selects one only when the current symptoms match it. A few would help most
remaining attempts on this task, whatever goes wrong next. Only those belong in L2. A
conditional skill ("when X, do Y") qualifies as long as following it would help most remaining
attempts.
A promoted rule is added to the prompt of EVERY remaining attempt, relevant or not, and it leaves
the retrieval catalog permanently. That is the cost of promoting it. Promote a skill only if
following it would help most remaining attempts.
Each candidate carries two usage figures:
picked M/N: selected on M of the N rounds on which it was offered.
new_bests=K: present on K rounds that improved the best result so far.
A high picked ratio with new_bests=0 is not grounds for promotion.
Promote nothing unless the evidence is there.
Do not propose a restatement of a rule that is already standing.
Return ONLY a JSON object:
{"promote_entry_ids": [], "rationale": "one sentence"}
No other text or markdown.
