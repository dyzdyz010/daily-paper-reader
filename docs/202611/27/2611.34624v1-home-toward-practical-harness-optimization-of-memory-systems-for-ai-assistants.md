## 摘要
长期运行的 AI 助手的记忆系统行为由 harness 控制，harness 包含用于记忆构建、维护、检索和答案生成的代码、提示与配置。然而，记忆系统 harness 的优化目前仍主要依赖人工，且仅进行不受限制的编辑并不能确保结构性改进。本文提出 HoMe，一个由评估驱动的框架，它迭代地评估候选 harness，并通过编辑任意先前已评估 harness 的任意部分来生成每个新候选。HoMe 将会话级记忆版本管理与执行轨迹相结合，识别跨案例的共享失败机制，并将其定位到相关会话和 harness 组件。它通过候选门控鼓励早期结构探索，并通过冒烟测试、自适应采样以及已构建记忆的复用来降低评估成本。我们使用开源记忆系统 ReMe 在两个大规模长时域记忆基准 LongMemEval-S 和 BEAM 上验证 HoMe。在每个基准仅进行六次正式候选评估的情况下，经过一次完整的初始评估后，HoMe 发现的 harness 在端任务性能上优于原本已很强的 harness，同时消耗的查询时 token 远少。代码见 https://github.com/agentscope-ai/ReMe。

## Abstract
The behavior of memory systems for long-running AI assistants is governed by a harness, which consists of the code, prompts, and configurations for memory construction, maintenance, retrieval, and answer generation. However, optimizing the harness of a memory system remains largely manual, and unrestricted editing alone does not ensure structural improvements. In this paper, we introduce HoMe, an evaluation-driven framework that iteratively evaluates candidate harnesses and derives each new candidate from any previously evaluated harness by editing any part of it. HoMe combines session-level memory versioning with execution traces to identify shared failure mechanisms across cases and localize them to the responsible sessions and harness components. It encourages early structural exploration through candidate gating and reduces evaluation cost through smoke tests, adaptive sampling, and the reuse of constructed memory. We validate HoMe with the open-source memory system ReMe on two large-scale long-horizon memory benchmarks, LongMemEval-S and BEAM. With six formal candidate evaluations per benchmark, after a full initial evaluation, HoMe discovers harnesses that improve end-task performance over the originally strong harness while consuming far fewer query-time tokens. The code is available at https://github.com/agentscope-ai/ReMe.

## 2. 方法论

### 2.1 总体框架

HoMe 是一个评估驱动的迭代优化框架，包含三个主要组件：

- **Developer Agents（开发者代理）**：包括 Optimizer Agent 和 Diagnoser Agent。前者负责生成候选 harness，后者负责归因失败。
- **Experiment Manager（实验管理器）**：维护 harness 仓库，控制候选准入与评估计划，记录所有评估结果。
- **Evaluation Environment（评估环境）**：在隔离的 Docker sandbox 中执行冒烟测试与正式评估。

优化从初始 harness \(h_0\) 开始。\(h_0\) 在全量数据上评估一次，作为 Git 仓库的根 commit；此后每个分支代表一个优化假设。每个迭代中，Diagnoser Agent 先诊断最近评估候选 \(h_b\) 的失败案例，再由 Optimizer Agent 选择一个已评估候选 \(h_j\)（\(j \le b\)）作为父节点并产生新候选 \(h_{b+1}\)。新候选需经过 gate 和冒烟测试才能进入正式评估，正式评估只在一个自适应采样子集 \(D_{b+1} \subseteq D\) 上进行。

### 2.2 长时域失败诊断

问题：单个查询的答案来自之前数百个会话累积的记忆，低分可能源于会话切分不当、后续维护覆盖了相关内容、检索未返回关键信息或答案生成阶段的错误。若无法定位到具体 harness 组件，迭代容易浪费在不相关的编辑上。

HoMe 的诊断设计：

- **会话级记忆版本化（session-level memory versioning）**：评估期间，每次会话结束后将记忆文件 Git commit 一次。因此任意中间记忆状态的检查点都可按需加载，两次相邻提交的 diff 恰好记录“该会话改动了什么”，无需读取完整历史。
- **轨迹引导归因（trajectory-guided attribution）**：对每个低分查询，代理从查询执行日志和记忆检查点向后追溯。首先判断检索结果 \(r_q\) 或最终记忆状态 \(m_{i,T_i}\) 中是否包含所需信息：若检索结果已包含，归因于 answer generation；若仅最终记忆包含，归因于 retrieval；否则归因于 construction。对于 construction 失败，还进一步通过会话间 diff 判断信息是否已写入、后来被哪个会话破坏或删除。
- **并行案例诊断（parallel case diagnosis）**：采用 map-reduce 方式。map 阶段多个 Case Study Agent 并行调查单个案例并返回紧凑的诊断结论；reduce 阶段 Diagnoser Agent 对比案例，识别跨案例的共享失败机制，并将诊断报告与具体 harness 代码绑定。这样能区分反复出现的 harness 缺陷与案例特有失败，同时降低个体诊断错误的干扰。

### 2.3 降低评估成本

评估总成本取决于三个因子：正式评估次数、每次评估案例数、每个案例的平均成本。HoMe 分别用以下机制压缩：

**冒烟测试与候选门控（smoke test + candidate gating）**：
- 冒烟测试在截断的真实案例上执行候选，拒绝运行期异常的 harness。
- 候选门控用于决定是否进入正式评估：前 \(B/2\) 个预算单位视为 exploration 阶段，优先接纳改变“运行时机制”（如记忆表示、construction、retrieval）的候选，拒绝只改提示词或参数的局部修补；后 \(B/2\) 为 refinement 阶段，允许提示和参数调优，从而平衡结构探索与后期精调。

**自适应案例和查询采样（adaptive sampling）**：
采样单元是案例或查询 \(v\)，通过指数移动平均维护其历史损失：

\[
\bar{\ell}^{(b)}_v = \alpha \left(1 - y^{(b)}_v\right) + (1-\alpha)\,\bar{\ell}^{(b-1)}_v
\]

其中 \(y^{(b)}_v\) 是单元 \(v\) 在候选 \(h_b\) 下的得分。采样优先级 \(r_v\) 和采样概率 \(p_v\) 定义为：

\[
r_v = \bar{\ell}_v + \lambda_s \log(1+\Delta_v) + \lambda_n \sqrt{n_v+1} + \lambda_u u_v
\]

\[
p_v = (1-\epsilon)\frac{\exp(r_v)}{\sum_{v'\in V}\exp(r_{v'})} + \frac{\epsilon}{|V|}
\]

其中 \(\Delta_v\) 表示该单元距离上次被评估的迭代数，\(u_v\) 衡量未复查的历史错误，\(n_v\) 是有效观测次数，\(\lambda_s,\lambda_n,\lambda_u\) 分别为对应的权重参数，\(\epsilon \in [0,1]\) 保留均匀探索的概率质量。采样先选择案例，若选中案例的总查询数超过 query cap，再对查询层执行同样策略。这样既聚焦高失败单元，又通过随机探索维持覆盖。

**记忆复用（memory reuse）**：
若候选 \(h_{b+1}\) 与其最近可评估祖先 \(h'\) 的 construction 过程等价（只改了检索/答案阶段，未动 construction 相关代码、提示或配置），则以概率 \(\rho\) 复用祖先已构建好的记忆状态，仅重跑 retrieval、answering 与 scoring，从而避免每次重新构建全部记忆的成本。否则重新采样并从头构建记忆。

### 2.4 实现与插件化

HoMe 在开源记忆系统 ReMe 上实现。作者将 ReMe 重构为“共享运行时 + 应用插件”的架构：

- 运行时负责任务执行、模型访问、存储等基础设施；
- 每个插件实例化特定应用的 harness，即 \(h = (c,p,\theta)\)。

这种分离让性能差异能被明确归因于 harness 变化，也方便将 HoMe 迁移到新应用。

## 3. 实验设计

### 3.1 数据集与基准

- **LongMemEval-S（LME）**：500 个单查询案例，平均历史约 11.5 万 token，覆盖 6 类问题。论文随机将其等分为训练集和测试集。
- **BEAM**：10 类问题，不同变体间数据独立。BEAM-100K（20 个案例，20 个查询/案例，平均历史 13.1 万 token）用于训练，BEAM-1M（35 个案例，平均历史约 104 万 token，最长约 152 万 token）用于测试，以验证跨记忆规模的泛化。
- **评估方式**：LLM as judge 按官方协议评分。报告 query 阶段平均输入/输出 token 以及平均 LLM 调用次数，且不扣除 KV-cache 命中带来的前缀复用。

### 3.2 对比方法

- 传统手动/静态方法：A-MEM、SimpleMem、ReMe。
- 自动化优化基线：MemPro（同样从人工调好的 ReMe 出发优化）。
- 各方法使用的底层 LLM 保持一致：记忆构建使用 qwen3.6-flash，其他使用 qwen3.7-max，嵌入使用 Qwen3-Embedding-0.6B。

### 3.3 主要实验

- **主实验**：在 LME 和 BEAM 上分别运行完整优化流程，比较 HoMe 与上述方法。
- **交叉迁移实验**：将在 LME 上优化的 harness 直接用于 BEAM-1M，反之亦然，检验跨基准的泛化能力。
- **稳定性实验**：在 BEAM 上运行两次独立搜索，考察结果稳定性。
- **效率消融实验**：逐步叠加并行化、采样、记忆复用，测量单次正式评估的耗时和 token 消耗。
- **优化轨迹分析**：逐候选分析 HoMe 和 MemPro 的搜索路径，呈现每次编辑的类型和规模。
- **案例研究**：解释几个典型的结构性 harness 修改。

## 4. 资源与算力

- **论文没有明确给出 GPU 型号、数量或加速器配置**。从实验描述看，正式评估以高并发方式执行（并发数为 28），并使用 Docker sandbox 和 warm sandbox pool，但没有披露底层 GPU/TPU 规模。

## 5. 实验数量与充分性

- **主实验规模**：两个大规模长时域基准（LME 和 BEAM），涵盖 5 个对比方法，加上 HoMe 有 6 种方法，覆盖率较好。

- **稳定性**：在 BEAM 上做了两次独立搜索，最终 harness 得分分别为 0.704 和 0.720，证明优化过程对随机因素有较好鲁棒性。
- **消融与效率分析**：提供了逐项效率消融和优化轨迹剖析，证据较充分。

- **整体评价**：从实验数量和设计角度看，研究覆盖面较广、对比维度多元，但测试集规模偏小，部分结论的外推需要谨慎。

## 6. 主要结论与发现

**核心实验结果**：

- LME 上 HoMe 得分从 ReMe 的 0.888 提升到 0.916，同时查询 token 从 43.9K 降到 17.9K（降幅 59%）。
- BEAM-1M 上得分从 0.650 提升到 0.704，token 从 101.8K 降到 60.4K（降幅 41%）。
- 与 MemPro 相比，HoMe 在 LME 上提高 10.4 pp、token 少 81.5%；在 BEAM 上提高 1.1 pp、token 少 7.6%。
- **跨基准迁移**：在 BEAM-100K 上优化的 HoMe harness 迁移到 LME 得 0.908（26.6K tokens），优于初始 ReMe；在 LME 上优化的 harness 迁移到 BEAM-1M 得 0.639（39.0K tokens），虽低于 ReMe 但 token 减少 62%，仍在 Pareto 前沿上。
- **优化效率**：HoMe 在 BEAM 上总优化 token 是 1.852 亿，比 MemPro 少 44.1%；第二个候选就已出现在 Pareto 前沿。
- **结构性发现**：HoMe 通过诊断自动发现了若干可复用的记忆机制，如日期分组目录、源感知检索、用户动作索引、证据压缩等，其中前两者在两个基准上独立出现，暗示这些是记忆系统设计中较通用的原则。
- **MemPro 的行为观察**：实验中的 MemPro 候选尽管被允许改代码，但 16 个候选全部只改提示词或参数，没有引入任何代码级机制；这直接说明需要显式的诊断和门控机制来引导结构探索。

## 7. 优点

- **问题定义清晰且重要**：把“记忆系统优化”抽象为 harness 搜索问题，并明确提出要同时优化效果与 token 效率。
- **诊断与定位机制扎实**：利用 Git commit 级别的记忆版本管理，通过 diff 追溯具体会话和具体 harness 组件，比仅凭查询日志的诊断更可靠。
- **分层诊断流程**：map-reduce + 案例代理，既控制上下文长度，又能发现跨案例的共享故障，减少偶然失败对整体判断的干扰。
- **成本控制机制合理且可组合**：冒烟测试、候选门控、自适应采样、记忆复用四个机制分别从评估次数、规模、单次成本三方面压缩，并具备一定的理论形式化。
- **结构性探索克制的诱导**：与端到端代码搜索不同，HoMe 使用 gate 强制早期探索运行时机制，使优化不仅能调参数、调提示，还能真正改变记忆结构。
- **实验相对透明**：报告了统计显著性、优化轨迹、token 消耗、时间开销，并公开了代码。
- **跨规模泛化验证**：用 BEAM-100K 训练、BEAM-1M 测试，验证了在比训练会话长约 8 倍的场景下依然有效。

## 8. 不足与局限

- **未披露 GPU 配置与算力总量**：只有耗时和 token 统计，缺乏 GPU 型号、数量、内存等关键算力信息，给复现性带来一定障碍。
- **测试集规模有限**：LME 测试集只 250 个案例，BEAM-1M 只 35 个案例，统计功效偏低。LME 得分提升未达到统计显著。
- **部分基线的调参可能不公平地偏向基线**：A-MEM 和 SimpleMem 在测试集上调参，有“作弊”风险，使 HoMe 的优势可能被低估，但从严格实验公平性角度看仍是一个瑕疵。
- **对 LLM 的固定性**：HoMe 框架明确将底层语言模型固定为外部不可优化部分，因此无法处理“换模型”带来的 harness 适配，也无法优化模型选择。
- **优化后的 harness 可解释性与可维护性未量评估**：虽然案例研究展示了具体机制，但未对 harness 的代码质量、可维护性做定量评估。
- **跨任务泛化尚不充分**：仅覆盖两个基准，两者都以 QA 形式为主，对更多样化的记忆任务（如工具调用、多步执行等）的适用性存疑。
- **对 LLM judge 的依赖**：成绩依赖于 LLM as judge 的可靠性，但论文未单独分析 judge 本身的偏倚。
- **优化过程中 token 数量是基于特定模型的**：如果更换底层模型，结论的数值结果可能变化较大。
