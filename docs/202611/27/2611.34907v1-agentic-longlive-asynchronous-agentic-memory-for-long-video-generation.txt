## Abstract 

Real-time autoregressive video generators stream minutes of video and accept new prompts on the fly, but struggle to keep people, objects, and places consistent over a long interactive story. Agent systems provide such memory for offline multi-shot generation, yet they read the whole script in advance, plan each shot before generating it, and regen-erate failed shots, which a live stream does not allow. We present Agentic LongLive, an asynchronous agentic mem-ory for long video generation. A memory agent on separate GPUs reads only the prompts revealed so far, never the gen-erated video, and keeps a text state and evolving images for every person, object, and scene. From this entity memory it composes a global image and a per-shot memory image, which an auxiliary GPU prefills into the generator’s atten-tion sink before the next shot starts, and writes entity cards for the prompts that name them, so the video never waits for memory and video errors are not written back. A small lan-guage model, trained with reinforcement learning and an image reward calibrated using downstream video outcomes, decides what to remember before the next prompt is known. On LongStory-Online, a new benchmark of 25 stories (857 shots) revealed one shot at a time, Agentic LongLive im-proves persistent-state accuracy of LongLive-2.0, its base generator, by 26.3 points, protagonist identity by 44.9, and revisited-place consistency by 40.4, at about 1% extra gen-eration time on H100. The full system streams faster than real time on one 8 ×B200 node with the generator in BF16 (34.3 FPS), keeps image quality stable over 14-minute sto-ries, and improves identity on two MiniMax-H3 generators, one of which, LongLive-H3, also runs in real time with it. To our knowledge, it is the first real-time video generator with text and image memory kept by an LLM agent. 

## 1. Introduction 

Video generation models are now strong enough to tell stories [33, 45, 51, 58], and agents that plan shots, track characters, and check results keep multi-shot videos con-sistent across scenes [26, 60, 62, 68, 86]. Live streaming, games, and world models need a different kind of gen-erator: autoregressive (AR), few-step models that stream long videos in real time and accept new prompts while they play [6, 19, 23, 28, 40, 47, 74, 77]. These generators have no agent. Their memory is the key/value (KV) cache: an attention sink that keeps the first frames [65, 74] and a short window of recent frames. Older content is forgotten, and what is kept is the model’s own output, so a wrong face or a lost object is copied forward [11, 28]. Adding an agent is hard because agents think slowly and 1arXiv:2611.34907v1 [cs.CV] 25 Nov 2026 real-time video cannot wait. A live session imposes four constraints that offline agent systems do not face: (C1) the future is unknown, so memory for a shot must be ready be-fore its prompt arrives; (C2) there is no length limit, so GPU memory must stay constant; (C3) the deadline is hard, so the video never waits for memory construction: planning, drawing, and prefilling must stay hidden, and once a prompt arrives only a quick choice among prepared memory is af-fordable; (C4) there is no rollback, so played shots can-not be repaired. Existing video agents rely on what a live session lacks: they read the whole script (C1), plan each shot while generation waits (C3), and inspect and regener-ate failed shots (C4) [26, 55, 60]. We present Agentic LongLive , an asynchronous agen-tic memory that gives real-time AR generators a long-term memory without slowing them down (Fig. 1). Asyn-chronous memory: a memory agent runs on its own GPUs and commits the memory for shot i before prompt i is re-vealed, and an auxiliary GPU prefills it into the generator’s KV cache, so the agent’s time is hidden behind generation. 

Open-loop entity memory: the agent reads only revealed prompts, never the video, so video errors are not written back. It keeps a text state and evolving images for every person, object, and scene, composes them into a global im-age G and a shot memory M that enter the frozen generator as attention sinks, and appends text cards of the entities a prompt names. Learning what to remember: before the next prompt is known, the agent must choose which entities to draw. We train a small language model for this with re-inforcement learning (RL), using a hindsight reward whose image term is calibrated using downstream video outcomes. We also build LongStory-Online, 25 stories (857 shots, about 150 minutes) with hidden annotations, where prompts are revealed one shot at a time and every shot is generated exactly once. On LongLive-2.0 [6], Agentic LongLive im-proves persistent state, protagonist identity, and location on scene changes by 26 to 45 points, adding about 1% gen-eration time on H100, and streams faster than real time on one 8 ×B200 node in BF16 (34.3 FPS). Its image qual-ity stays flat over 14-minute stories, its identity gains carry over to two few-step MiniMax-H3 generators [43, 45], with LongLive-H3 also in real time on B200 (1.45 ×), and RL lets an 8B planner replace the 35B planner. We contribute: • an asynchronous agentic memory system that hides agent latency behind real-time generation with constant GPU memory and no length limit, to our knowledge the first real-time video generator with text and image mem-ory kept by an LLM agent; • an open-loop two-layer memory as attention sinks of a frozen AR generator, with entity cards in the prompt; • an RL recipe with a video-calibrated reward that teaches a small LLM what to remember, and the LongStory-Online benchmark. 2.1. Online long-video generation

2.2. Asynchronous agentic memory 

Ranks and one-way data flow. DiT ranks generate video (Fig. 2). Auxiliary ranks run a decoder that streams la-tents through the VAE, like the asynchronous decoder of LongLive-2.0 [6], and a prefill worker that holds a copy of the DiT weights, encodes memory images with the frozen VAE, and computes their sink K/V, each on its own GPU. 

Agent ranks host a vision–language model that plans and checks, and an image model that draws memory images. Data flows one way: from the agent to the prefill worker, 2then to the DiT, and on to the decoder for display. The agent never waits for decoding, and memory K/V are ready before the shot that uses them (GPUs per role in Sec. 3.1). 

Commit and swap. Memory for shot i is prepared while shot i − 1 is generated, between the reveals of pi−1 and 

pi (Fig. 2). Version 0 is committed as soon as it is drawn, even if it fails its check, so checks do not cause lag ( G fol-lows a stricter rule, App. B), and is prefilled at once. If time remains, the agent may redraw an image that its check flags. The new version replaces the committed one only if it passes and scores no lower. At the boundary, the DiT swaps in the newest fully prefilled version as a whole, with-out waiting for one in progress, so no shot mixes two ver-sions. If no new version is ready, it keeps the previous mem-ory (lag, Sec. 2.1). The agent thus has one shot’s time per memory (budget in App. B), and as the video never waits, the generator alone sets the throughput. 

2.3. Two-layer memory 

Layer 1: entity memory. Every person, object, and scene is an entity with a text state and images (Fig. 3a): views for people and objects, and an empty plate for scenes. After a prompt is revealed, the agent draws new or changed entities. Since the next prompt is unknown (C1) and played shots are final (C4), memory holds the current belief about each entity. Images keep only attributes that persist across shots (identity, clothing, dirt, damage, assembly) and leave pose and action to the next prompt. Each state records its source, so a contradicting later prompt can revoke it (App. C). 

Layer 2: memory images. Generators cannot read an en-tity database, so the agent composes two images for them (Fig. 3b). The global image G shows the protagonist and long-term key objects in their current state on a plain stu-dio backdrop, and is refreshed when one of them changes. The shot memory Mi shows the current scene and its active entities, one per shot. G thus carries identity and state but no place, which is left to M and the prompt. Both are com-posed with entity images as references rather than redrawn from text, so an object keeps its look across shots. Entity images are drawn or edited in the background and checked once. The rules for refining G and M are in App. B. 

Sink injection. G and M are encoded by the frozen VAE and prefilled as sink K/V (Fig. 3c). Only the foreground of 

G enters the sink (Fig. 3b): the agent segments its members and drops the backdrop, which MiniMax-H3 would other-wise copy into new scenes as a grey studio. LongLive-2.0 keeps the whole G (App. C). G is conditioned on the de-scription of its members and stays as the permanent global sink. Each M is conditioned on the revealed prompt it was drawn from. Shot i starts from window [G, Mi−2, Mi−1]

as a new shot : an 8-frame gap follows the latest M and the first chunk is prefixed with “The scene transitions.”, the multi-shot format of the base model [6]. That chunk is pinned as the shot sink, and the window rolls to [G, first chunk, recent chunks ]. M thus sets the appearance at the start and then leaves, so the video follows the prompt in-stead of copying the layout of the memory image. Each M

is prefilled once while attending to G and earlier M, so its K/V carry the memory history. When G changes, the M

blocks are prefilled again under the new G.

Scene routing. Mi−1 shows the previous location, but the next prompt may continue there, move to a new place, or re-turn to an earlier one. When pi is revealed, the agent’s LLM reads it with the names and descriptions of the locations it has drawn and picks one of them or new , with decoding con-strained to these options. If it picks the location of Mi−1,the memory is kept. If it picks another known location, the newest M drawn there is recalled and injected as [G, Mloc ].For a new place, only G is injected (Fig. 3c). The choice reads only revealed prompts and committed memory, and no memory is built after pi arrives. The prefill worker keeps the newest M of every known location prefilled under the current G, so a recall only swaps blocks. On LongLive-2.0, routing is the only model call on the critical path (Sec. 3.3). 

Entity cards. Images carry places and a look that words do not pin down, while the text encoder reads attribute words directly, so memory also enters as text. When pi

is revealed, every entity of the committed memory whose name occurs in pi (whole-word string match) gets a card appended after the prompt: its name, description, and per-sistent state (example in App. C). The agent writes these texts in advance, so only string matching remains after the prompt. Like images, a card reflects memory up to shot 

i−1: a change stated in pi is in the prompt itself and enters the card from the next shot on. 

Other generators. The same memory drives two chunked-AR versions of MiniMax-H3 [45], RAVEN [43] and LongLive-H3 (Sec. 3.1), which take G and the routed 

M as sink chunks and entity cards in their prompt. Where text enters decides the cost of memory. With cross-attention, as in LongLive-2.0, memory K/V depend on the memory images and their captions from earlier prompts, not on the newly revealed prompt, and are fully prefilled ahead of time. With text at the start of the sequence, as in MiniMax-H3, they depend on the prompt and are computed once after it arrives (Sec. 3.3).

State and action. The policy sees the entity bank as text, the four newest prompts, and a slot budget. For each shot it writes one JSON object with every text role of the agent: entity state updates, drawing prompts, the members of G

(≤3) and M (≤4), and the sink captions (fields in App. D). 

Hindsight reward. After each decision, a scorer com-pares it with hidden annotations of later shots, which are used only for scoring. The reward of a decision is 

r = 0 .35 rtext + 0 .3 rimg + 0 .15 rprec + 0 .05 rret − rpen . (2) The text term rtext asks an LLM judge whether the persistent states that the next six shots need, but terse prompts will not restate, are remembered correctly, missing, or wrong. The terms rprec and rret reward precise and retained facts, and 

rpen penalizes size, false facts, and length. Recalled facts alone do not make better videos (Sec. 3.5): the few image slots must also hold the entities that the next shot shows. The image term rimg therefore renders G and M from the chosen members with the agent’s image model, and a VLM checks whether each entity of the next shot is recognizable and correctly drawn. It rewards each such entity in G or M

and charges each member of M absent from the next shot. 

Calibrating the image term with video outcomes. Gen-erating videos in the RL loop is too slow, so we calibrate the image term on existing videos. A regression of judged en-tity attributes in real videos on memory composition shows that an on-screen entity gains about as much state accuracy in G as in the latest M, while each absent member of M

costs a little. Normalizing these effects gives the weights of 

rimg (App. D). A memory slot is thus valued by what it adds to the video, not by how many facts it recalls. 

Training. A teacher plays 56 training stories online. Rejection-sampling fine-tuning [81] on its best outputs warm-starts the policy, and GRPO [54] with each shot as a decision then optimizes this reward (App. D). 

## 3. Experiments 

3.1. Setup 

Protocol and benchmark. Every method sees one prompt per shot, generates each shot once, and never reads 4future prompts. Regeneration and best-of-N are not al-lowed, but a baseline keeps its own closed-loop mecha-nisms. LongStory-Online has 25 stories, 857 shots, and about 150 minutes of video: nine stories written by hand (211 shots) and sixteen LongStory-Hard stories designed by an LLM with states accumulated by code (646 shots). Sto-ries have more entities than memory slots, long absences and revisits, persistent changes (clothing, dirt, damage, as-sembly), and prompts that overturn earlier inferences. Each shot has a hidden annotation of entities, persistent states, and location, frozen before any method was run. Prompts are terse , like real user input: a place or person is described once, and later prompts use names or “back in the kitchen”. 

Baselines. LongLive-2.0 [6] shares our backbone and keeps its built-in memory: sinks on the first chunk of the video and of each shot, and a KV window carried across shots. Four open AR models on Wan2.1-T2V-1.3B, 

Self-Forcing [28], CausVid [77], Causal-Forcing [89], and 

Rolling Forcing [40], run one rollout per story with the prompt switched at each shot. Self-Forcing breaks down within minutes, as in its official code (83% of its shots have severe artifacts), so we do not rank it. On MiniMax-H3 [45], we test two few-step chunked-AR generators: RAVEN [43] and LongLive-H3 . We distill LongLive-H3 from MiniMax-H3 by causal distribution matching distillation (DMD) [76] on prompts alone. It generates video and audio in chunks of about 0.7 s, each attending to the text, the first chunk, and the two previous chunks (App. C). Without memory, each 8 s shot is generated from its prompt alone. A sec-ond baseline carries K/V across shots as LongLive-2.0 does (App. C). The non-real-time systems StoryMem [83] and 

StoryEngine [60], an offline variant of ours, SkyReels-V2 [5], and all baseline adaptations are in App. F. 

Metrics. A VLM judge (Gemini 3.8 Flash), different from every model of the real-time agent and of RL train-ing, compares four frames of each shot with its annotation: 

State (persistent attributes correct), Identity (the visible pro-tagonist matches its description), and Location (on scene changes). Same protagonist compares each shot whose plan shows the protagonist with the method’s first shot of it (0 if the protagonist is missing). Revisit rates whether a return shows the same place as the last visit and counts only re-turns where both shots are at their planned place [60]. We also report VBench imaging quality [29] and the share of shots with severe artifacts. Framing, imaging drift [40], and ArcFace face identity (MIR [60]) are in App. E and H. Re-judging agrees on 92–96% of decisions. As the same model also wrote the Hard stories, a second judge from another family (GPT-5.5) re-judged 14 runs and confirms 87 of the 94 significant comparisons, with no sign flip (App. E). Automated-metric differences quoted in the text are dif-ferences of table entries, significant unless noted (a story-clustered bootstrap 95% interval excludes zero). 

Implementation. LongLive-2.0 runs Wan2.2-TI2V-5B [58] in BF16 with 4 steps and 10.5 s shots. The agent checks images and routes scenes with Qwen3.6-35B-A3B [52] and draws with FLUX.2-klein-4B [2], each on one H100. In the full system, the RL planner (Qwen3-8B [73] with LoRA [24]) writes the memory on a third H100. Without RL, the 35B model also plans. The full system thus uses six H100s (DiT 1, auxiliary 2, agent 3), against two for LongLive-2.0 alone (DiT and asynchronous decoder). Memory streams come from the live agent against a stand-in generator with the same shot time (zero lag on 97–99% of shots) and are replayed into each generator, pixel-identical to a live run. On LongLive-2.0, rows with the RL planner pair each of three planners, trained with different seeds, with one video seed. 

3.2. Main results 

Same backbone. On LongLive-2.0, our system and the built-in memory share the generator and the prompts, so the comparison isolates memory. The full system improves all five consistency columns (Tab. 1). State accuracy rises by 26.3 points, and revisit consistency from 15.0% to 55.4%. Imaging quality also improves and, unlike with the built-in memory, does not decay over a story (Fig. 6). The cost is about 1% generation time on H100 (Sec. 3.3). Sections 3.4 and 3.5 separate the contributions of memory images, scene routing, entity cards, and the RL planner. 

Other real-time AR models. The four Wan2.1 models run a smaller backbone at a lower resolution, so this com-parison mixes backbone and memory. Without our memory, LongLive-2.0 already leads them in state and location, but not in identity, same protagonist, or revisit ( e.g . 44.1% vs .59.8% identity for Causal-Forcing). With our memory it leads in all five consistency columns (Tab. 1, top, all sig-nificant). Rolling Forcing has the highest imaging quality (0.748) but rarely follows a scene change (33.1% location). 

Other backbones. On the MiniMax-H3 generators, our memory mainly improves identity: it rises from 61.0% to 98.0% on RAVEN and from 58.2% to 96.8% on LongLive-H3. Non-real-time references. On the same Wan2.2-5B backbone and keyframe model, our offline variant (the same memory with API models and synchronous refinement) gains 9.3 state points over StoryEngine but trails it by 15.7 revisit points (App. F). On LongLive-2.0, our real-time full system reaches 93% of StoryEngine’s state accuracy and identity at 1/47 of its time per second of video. 

User study. Thirty-two participants each evaluated ten stories, viewing four shots spread over each story, and picked the best version on four criteria (App. I). For per-sistent state, our full system receives a story-averaged best-version vote share of 98.8% against the built-in memory of LongLive-2.0, and 97.8% in a three-way choice with the independent-shot and carried-K/V versions of LongLive-H3 (ties split the vote). Identity and location receive 94 to 100%. Ours also receives every visual-quality vote on LongLive-2.0, whereas on LongLive-H3 these votes split between independent shots (55.1%) and ours (43.6%). 

Qualitative results and long horizon. In Fig. 5, only our memory carries the presenter’s stain, black T-shirt, and shave through the eight-minute tour. Over 14 minutes (Fig. 6, state in App. C), our identity and imaging qual-ity stay flat, whereas LongLive-2.0 loses identity after two minutes and imaging quality throughout.

3.6. Other applications 

Because the agent only decides what the generator sees and leaves the generator unchanged, we also test it on robot video models (App. G). In robotics, a camera that stays close to an object for longer than the context window loses the rest of the scene. On the robot video model of Long-WAM [27], the original model then turns to a different scene. An observation-based variant of our memory, which stores the initial scene and an object crop in the sink, keeps both and brings them back (Fig. 7). This variant differs from the agent of Sec. 2: its memory pictures are frames that the camera has already shown, not drawn images. For long robot tasks (App. G), it also reads the generated video (closed loop) and sees each instruction one segment before it plays, because a robot acts in one continuous scene whose state depends on what was generated. 

## 4. Conclusion 

We presented Agentic LongLive, an asynchronous agentic memory for real-time long video generation. A memory agent that reads only revealed prompts keeps entity memory and commits memory images that an auxiliary GPU prefills into the generator’s attention sink, so the video never waits for memory, and RL teaches a small planner what to remem-8ber. On LongStory-Online, this improves state, identity, and place consistency of LongLive-2.0 at about 1% extra gener-ation time and streams faster than real time in BF16 on one B200 node. Image quality stays flat over 14-minute stories, and the identity gains carry over to two MiniMax-H3 gen-erators, with LongLive-H3 also in real time. 

Limitations. Memory needs extra GPUs for the agent ranks and the prefill worker (Tab. 2). On LongLive-H3, it also leaves per-shot visual quality to the base model: human raters judge it no better than that of independent shots.

## A. Related Work 

Real-time AR video generation. Diffusion Forcing [4] and CausVid [77] make video diffusion causal. Self Forc-ing [28] and its successors [11, 40, 43] close the train–test gap with self rollouts and few-step distillation. MAGI-1 [53], SkyReels-V2 [5], Krea Realtime [34], APT2 [38], and StreamDiT [32] scale this up. To run without a length limit, these models keep a fixed window of recent frames and an attention sink [65]. Rolling Sink [35] keeps this cache close to what the model saw in training, without re-training, so rollouts stay stable far beyond the training hori-zon. LongLive [74] adds a frame sink and KV re-caching for prompt switches. LongLive-2.0 [6] adds multi-shot sinks and parallel inference, and LongLive-Plug [75] distills few-step and long-video LoRAs once and plugs them into other models of the same backbone family. Other works pack or route longer context [3, 63, 84], split the cache into sink, archive, and working banks [82], or retrieve earlier frames by the current prompt [30]. In all of them, memory lives inside the generator and is built from its own frames (closed loop). Our memory lives outside the generator and is written by an agent from the prompts alone. 

Agents and memory for multi-shot video. Agentic sto-rytelling systems write scripts, draw keyframes, and repair shots with VLM feedback [25, 26, 55, 59, 60, 62, 68, 71, 86]. The closest, StoryEngine [60], keeps structured en-tity states and canonical references. All of them run of-fline: they see the full script and can select or regenerate shots. Concurrent works bring agents closer to streaming. AgiWorld [15] links a planning agent and a video world model through a shared spatial memory. Wizard [64] con-trols a real-time game world model with a VLM agent that turns instructions into programs over scene geometry. Agi-World does not report real-time operation, and Wizard’s agent edits scene geometry and a symbolic game state, not image memory. To our knowledge, ours is the first real-time video generator with text and image memory kept by an LLM agent: the video never waits for the agent, and the whole system streams faster than playback. Other meth-ods keep memory inside the model. They carry keyframes or long context across shots [20, 44, 66, 83] or index past frames by pose and time [36, 67, 79], so their memory comes from generated pixels. Reference-to-video mod-els [13, 17, 41, 45] inject a fixed set of reference images. We instead decide what to store and update it during the session, and our memory images can serve as references. 

Asynchronous agents and learned memory. Robot sys-tems run a slow planner beside a fast controller [1, 46, 56, 57], and LLM agents overlap thinking with waiting [9, 10]. Our slow agent instead must commit versioned memory to a separate real-time generator before a deadline. LLM agents also learn what to store [8, 49, 70, 72, 78, 88], and RL tunes prompts for image and video models [7, 21, 31, 61] with learned judges [22, 39, 69]. We combine the two. One LoRA-tuned planner writes the structured memory and the text that the frozen generator reads, and its image reward is calibrated on real videos. 

## B. Asynchronous System and Speed 

Measurement. DiT FPS is the number of frames di-vided by denoising time, excluding VAE decoding, as in LongLive-2.0 [6]. End-to-end FPS divides frames by wall-clock time including decoding, memory prefill, shot-boundary swaps, and waiting. The real-time factor is video seconds over wall-clock seconds. Overhead is the rela-tive increase in wall-clock time over the base generator on the same hardware, prompts, and video length. Each method is warmed up and loaded once. Events (start and end of each DiT chunk, end of each decode, memory com-mit, prefill done, boundary swap) are timestamped after 

cuda.synchronize , and all numbers come from one timing log per run. DiT throughput varies by ±1–2% across GPUs, so overheads within ±2% are treated as noise. The H100 timing runs on LongLive-2.0 have no entity cards, which the agent writes off the critical path. 

Timing runs and quality runs. Speed and quality are measured in separate runs. The quality runs generate many 13 stories, seeds, and arms in parallel on H100 and A100 GPUs, so each LongLive-H3 video uses one GPU, and each RAVEN video its official four (Sec. C). The MiniMax-H3 times of Tab. 1 come from one session on one H100 node with four GPUs per video (LongLive-H3 with tensor paral-lelism), on two stories (20 shots) after a one-shot warm-up, with the overhead paired per shot. GPU count, parallel lay-out, and faster kernels keep the model, the sampler, and the random draws, and change only BF16 rounding. In blind pairwise judgments, the optimized runtimes do not differ significantly from the release (Tab. B2), and neither does the same code on B200 instead of H100. 

Deployed agent. Qwen3.6-35B-A3B-FP8 [52] with multi-token prediction [12] on SGLang [85] checks images (0.85 s) and routes scenes (0.06 s), and FLUX.2-klein-4B [2] draws (1.2–2 s), each on one H100. The RL planner, Qwen3-8B with LoRA served with EAGLE-3 [37] on a third H100, takes 3.5 s per update in a single live run. Without RL, Qwen3.6-35B also plans. We chose these models on recorded agent requests. FLUX.2-klein-4B scores below GPT Image but is more than ten times faster, and none of the other fast open image models we compared is better under both of our judges. An API agent (Gemini and GPT Image) needs about 56 s per update and lags 3.6 shots on LongLive-2.0, so it serves only the offline variants, whose shots take minutes. An image passes its check if the checker accepts it, or if it scores ≥6/10 and shows the required persistent state. Decoding and prefill use one auxiliary GPU each. Over a 40-shot run, the time per shot stays at 16.0–16.2 s. 

B200. On one 8 ×B200 node (180 GB each), we keep the story, harness, and GPU layout of Tab. 2 (DiT 1, auxil-iary 2, agent 3) and reveal each prompt at playback pace (every 10.54 s), as a live user would, instead of when the previous shot finishes. Each cuDNN attention call matches FlashAttention-2 to one or two BF16 rounding steps, but whole videos diverge as with any kernel change, so all quality numbers on LongLive-2.0 and on the chunked-AR MiniMax-H3 generators use the evaluated BF16 path (the bidirectional generators of Tab. With BF16 weights, cuDNN attention, a compiled VAE decoder, and decoding overlapped across shots, LongLive-2.0 streams at 34.1 FPS (1.42 ×) and the full system at 34.3 FPS with ev-ery update in time (Tab. With a stand-in gen-erator at the same pace, an agent on H100 GPUs has 34 of 39 updates ready in time (Tab. B3). A fourth agent GPU is an option for longer prompts.

Scene routing. The router is the agent’s LLM (Qwen3.6-35B-A3B-FP8, thinking off, temperature 0). Its input lists the locations of the committed M images, each with the name and description the agent wrote for that scene en-tity from prompts up to pi−1, the location of Mi−1, and the full prompt pi. The output is constrained to one of the names or NEW. The system prompt reads: “For ev-ery location that earlier shots were filmed in, the memory keeps a picture. . . . If it takes place in one of the known locations, whether it continues in the previous shot’s lo-cation or returns to an earlier one, answer with the exact name of that location. If it takes place in a location that is not in the list, answer NEW. Judge by the physical set-ting the camera shows, not by which characters or objects are mentioned.” It was written once and not changed after seeing any decision, and nothing in the router is fitted to LongStory-Online. A recalled M is written right after G,attends to G, uses its source prompt as text, and the video starts 8 frames later, as for a regular M. On an H100 the call takes 0.06–0.12 s. The auxiliary rank keeps [G, Mloc ] pre-filled for every known location (at most eight), so a recall only swaps blocks. This gives bit-identical video to pre-filling at the boundary, which would cost 0.87 s per recall. The router keeps Mi−1 on 69% of shots, recalls on 17%, and drops on 14%. Against the hidden annotations of the 832 shot boundaries of LongStory-Online, it injects an M

of the wrong place 19 times (scene gate: 84), an M of the right place 696 times (gate: 568), and recalls the right place on 94% of the returns whose location is in memory. The keyword scene gate of Tab. 3 kept Mi−1 when the opening sentence named its location or shared 20% of content words with the opening of pi−1, and otherwise injected only G.Shared words such as “back” or “still” made it keep the old place on many returns and changes. 17 H3 prompts. MiniMax-H3 generates audio and video from a sectioned prompt. Before any run, each terse prompt is converted once into this format by Gemini 3.8 Flash from that prompt alone and a few story-level constants (the pro-tagonist’s name and voice, the music): one continuous 8 s shot with an opening phrase (shot size, place, where the protagonist is), the action in timeline order with 0–2 short spoken lines, a soundscape, and the music. The conversion keeps every fact of the terse prompt and adds no appearance, clothing, colour, layout, or prop detail, so the H3 prompts stay as terse as the originals. All H3 rows, with and without memory, use the same H3 prompts, and the routing deci-sions of the H3 rows are made on them. 

LongLive-H3. We obtain LongLive-H3 from MiniMax-H3 by causal distribution matching distillation (DMD) [76], with the chunking and few-step schedule of RAVEN [43]. The frozen, bidirectional MiniMax-H3 serves as the real-score teacher. The student is a LoRA of rank 128 on the frozen backbone, and a second rank-128 LoRA serves as the fake-score model, trained by flow matching on the stu-dent’s own rollouts. The student is trained with the nor-malized DMD surrogate, and fake-score and student up-dates alternate 5:1 after 50 fake-score-only warm-up up-dates. Training uses prompts only, without real video or audio: 1,024 original single-shot prompts from SMD-H3-T2VA-100K and 256 multi-shot prompts that we rebuilt from SMD. Training clips have 124 frames at 1344 ×768 and 24 fps with jointly generated 32 kHz stereo audio, i.e .37 video latents and 207 audio latents per channel. Each clip is split into eight chunks, seven of 5 video latents (about 0.7 s) and a 2-latent tail, with the audio split at the same boundaries. Attention is block-causal: each chunk attends to the text, the first chunk as a sink, the two previous chunks, and itself, and earlier chunks are fed as clean context at clock 0.999. We train on 32 GB300 GPUs with a global batch of 64 (2 per GPU), learning rates of 2 × 10 −6 for the student and 10 −5 for the fake-score model, and EMA de-cay 0.99. The released checkpoint is the EMA after 200 student updates (1,000 fake-score updates). At inference, LongLive-H3 takes 3 steps per chunk and generates 8 s shots (192 frames), longer than its training clips. With a KV cache that reproduces its chunked sampler, a shot takes 50.2 s on one H100 (116 s on A100), and all quality results use this one-GPU path. Table 1 times it on four H100s with tensor parallelism (Sec. B). RAVEN generates 1376 ×768 as released, with 4 steps per chunk. 

K/V carried across shots. Without memory, every MiniMax-H3 shot is a separate rollout from its prompt. The second baseline carries K/V across shots as the built-in memory of LongLive-2.0 does, with the mechanism of our sink: the first latent frames of the story’s first shot (a global sink) and the last latent frames of the previous shot are writ-ten as one clean chunk after the new shot’s text, so their K/V are recomputed under the new prompt (LongLive’s K/V re-cache [74]). RAVEN carries four global and six recent frames (1 s, its K/V window). LongLive-H3, which holds the whole model on one 80 GB GPU in the quality runs, carries one global and two recent frames, the size of our memory chunk. The carried frames end eight video frames (1/3 s) before the new shot, as in LongLive-2.0’s multi-shot format, the shot starts at 2 s, as with our memory chunk, and prompts, seeds, and everything else equal the rows with-out memory. Carried K/V raises identity over no memory (RAVEN 61.0% → 91.2%, LongLive-H3 58.2% → 76.0%, both ∗), though less than our full system (96.8–98.0%), but shots continue the previous one: location on scene changes falls to 20–26% (85–86% without memory), and revisits do not improve. Severe artifacts also accumulate along the story (RAVEN 1.6% of shots 1–10 and 14.9% after shot 20, LongLive-H3 3.6% and 17.5%), mostly colour distortion or corrupted frames, as each shot continues frames that the generator produced under another prompt. With our mem-ory, which comes from the agent rather than from the video, they stay flat along the story (3–6%).

Bidirectional generators. Sinks need no causal attention. MiniMax-H3 packs the text, the condition images, and the generated video into one sequence on a shared time axis (40 positions per second). Condition rows stay clean and only the video is denoised. Ref2VA places each reference one position after the previous one and starts the video right af-ter the last. For a sink, we move the memory pictures to 0, 0.25, and 0.5 s and the video to 2 s, as on LongLive-H3, and replace the per-picture prompt lines by one sentence say-ing that the pictures are frames of earlier shots and that the shot starts after a cut. Rows and computation equal those of Ref2VA references, but the pictures are attended to at every denoising step instead of being prefilled once, and memory can change only between shots. With the per-picture lines of the LongLive-H3 prompts, Pika-H3-Flex often opens on the memory pictures, and the judge prefers the single sen-tence on 45 of 54 shots.

We therefore keep only the foreground of G. Entity layer. The entity layer follows from the online set-ting. Views: each character and object is drawn in two views on a plain light-grey backdrop, a front view (full body for characters, the whole object for objects) and a three-quarter view. Each scene is drawn once as an empty plate, a wide view of the place without people. The three-quarter view is drawn with the front view as a reference, so both show the same entity. G and M are composed from the front views and the plates only, so on LongLive-2.0 the three-quarter views never reach the generator. They are used only when entity images themselves are passed as references ( Integra-tion with LongLive-H3 ), where all views of a selected entity are listed together. Persistent versus transient (C1): entity images show only attributes that persist across shots, such as identity, clothing, dirt, damage, or assembly progress. Pose, action, and held objects stay neutral because the next prompt decides them. Memory as current belief (C1, C4): 

each state records its source shot and whether it was stated or inferred, and a contradicting later prompt revokes it and triggers a redraw. Refinement: a new entity is drawn from text and a changed one as an edit of its latest image, retried from its first image if the edit fails. Each entity image is checked and repaired at most once, and if it still fails, the entity keeps its previous image. Memory images are re-fined as in Refinement (Sec. B). These choices decide what memory means when the next prompt is unknown, and they matter whenever an image would otherwise show a pose or a revoked state. 

## D. Memory Planner 

Training details. The policy is Qwen3-8B with LoRA (r=32 , α=64 , all linear layers) and the deployed system prompt and JSON schema. Training uses 56 stories plus 8 development stories written by Qwen3.6 (24–32 shots each) whose per-entity persistent states are accumulated by code. RFT uses 2,865 examples (best of 4 by reward from 3,138 teacher states). GRPO treats each shot as one decision and runs 80 steps with 8 states × 8 samples per step, the token-level loss of DAPO [80], no KL term, zero-variance groups dropped, temperature 0.9, learning rate 2×10 −5,gradient clipping 0.5, group standard-deviation floor 0.1, and one-step off-policy pipelining. Each seed trains on one H100 and shares rollout, judge, and image services on two 8×H100 nodes (about 2–2.5 hours for three seeds in paral-lel). The training judge is Qwen3.6-35B-A3B and the test judge Gemini 3.8 Flash with the same prompts. They agree on 79–83% of items (per-decision correlation 0.66–0.77). 

Reward details. In Eq. (2), the text judge scores each per-sistent state that the next six shots need +1 if memory holds it correctly, 0 if it is missing, and −1.5 if it is wrong. The image term renders G and M with a fixed seed. Each en-tity of the next shot that the VLM finds recognizable and correctly drawn earns 0.51 if it is in G and 0.49 if it is in M (down to half if drawn in a wrong state), and each member of M absent from the next shot costs 0.11. These weights come from a regression of 3,867 judged entity at-tributes from real videos on memory composition, with story and planner fixed effects: an on-screen entity gains 

+9 .0 points of state accuracy (95% CI [4 .7, 13 .8] ) in G and 

+8 .7 [4 .6, 12 .4] in the latest M, while each absent mem-ber of M costs −1.9 [ −3.7, 0.0] . Normalizing these effects gives 0.51, 0.49, and 0.11.

## E. Benchmark and Metrics 

Terse prompts. Terse prompts are rewritten from full prompts by Gemini 3.8 Flash. The first shot is unchanged, and new places keep their description, while continuing or revisited places become one phrase (“still in”, “back in”). The protagonist and earlier entities are named without ap-pearance or state, changes that happen in the shot remain as actions, and camera motion is kept. Automatic checks re-ject rewrites that repeat attribute phrases of a character card or whose place part exceeds 15 words for continued places (at most two retries). 

LongStory-Hard. Sixteen stories with about 40 shots and 13–14 entities each (12–14 recurring, 2–4 per shot), with 7–36 returns after 5+ absent shots per story. They are writ-ten by Gemini 3.8 Flash, a different model from the one that wrote the training stories, on topics disjoint from train-ing, development, and hand-written stories. Hidden states are accumulated by code from initial attributes and per-shot persistent changes. The manifest is frozen with a hash be-fore any method is run. 

Judges. The shot judge scores location, framing, content, identity, persistent states, and artifacts from four frames (4, 35, 65, 97% of the shot), and the pairwise judge scores same place and same protagonist (1–5, camera changes not penalized). The pairwise metrics are described below. Re-judging 211 shots agrees on 95.7% (location), 94.8% (fram-ing), and 92.3% (state items). 

Second judge. E1). These runs use a G that also shows the cur-rent scene instead of the plain-backdrop G of Sec. 2.3, so their values differ slightly from Tab. 1, but the compari-son concerns the agreement of the two judges on the same shots. Judge prompts. The shot judge receives the system prompt below, then the place list (the setting sentence of the first prompt of each annotated place), the protagonist card, the planned camera and content, the expected states, and the four frames. The pair judge receives its system prompt, the place name, the protagonist card, and two frames of each shot. Both run at temperature 0 with JSON output. 

Shot judge (system prompt) 

You evaluate one shot of an AI-generated long video against a hidden plan. You see FRAMES of the shot in time order (first frame, about 1/3, about 2/3, last frame). Judge only what is visible. Return JSON: {"opening_location": str, "location": str, "shot_size": "extreme close-up|close-up|medium|wide", "framing_match": bool, "content": 0|1|2, "protagonist_visible": bool, "protagonist_match": bool|null, "facts": [{"key": str, "verdict": "confirmed|contradicted|not_visible"}], "artifacts": bool, "notes": str} - opening_location: where the FIRST frame takes place; location: where most of the shot takes place. Each is exactly one key from LOCATIONS, or "other". - framing_match: true if the camera distance/angle and the main subject agree with PLANNED CAMERA and PLANNED CONTENT (e.g. a planned close-up of hands on a part must not be a medium shot of the person standing). - content: 2 if the main subject and action of PLANNED CONTENT are clearly shown, 1 if only partly (right subject or place but the action is missing or different), 0 if not shown. - protagonist_match: if the PROTAGONIST is visible, whether it matches the identity description (face, species, body, age; ignore clothing and accessories, which may change); null if not visible. - facts: one entry per EXPECTED STATE key: "confirmed" if clearly visible and correct, "contradicted" if visible and different, "not_visible" otherwise. - artifacts: true only for severe failures: a ghosted overlay or blend of two different images, melting or broken anatomy, frozen or corrupted frames. 

Pair judge (system prompt) 

You compare two shots, A and B, of an AI-generated story video. The story says both take place in the same location. You see two frames of shot A, then two frames of shot B. Judge only what is visible; a different camera angle, distance or time of day is expected and must not lower the score. Return JSON: {"place": 1-5, "person": 1-5 or null, "shared": str, "differs": str} - place: how consistent the place is. 5 = unmistakably the same place: specific furniture or landmarks, layout, materials and colours match; 4 = the same place with minor inconsistencies; 3 = same kind of place with a few specific matching details but clear differences; 2 = same kind of place, no specific details match; 1 = a different kind of place. If a shot is a close-up, compare whatever background, surfaces and props are visible. - person: if the PROTAGONIST is visible in both shots, how consistent their identity is (face, hair, build, species and markings; clothing, dirt and accessories may legitimately change). 5 = clearly the same individual, 3 = similar but uncertain, 1 = clearly a different individual; null if not visible in both. - shared / differs: the main matching and differing details (short). 

Cross-shot metrics. Same protagonist fixes the shots that count from the plan: the evaluation judge reads only the 22 hidden plan of each shot (planned camera, content, and en-tities present), never a video, and decides whether it shows the protagonist recognisably (face, or head and body for a non-human protagonist, but not only hands, from be-hind, or tiny). This holds for 349 of 857 shots (41%), with a prompt written once. Each of these shots scores (rating −1)/4 against the method’s first shot of the protago-nist (four frames of each shot, compared on face, hair, build, age, species, and markings, while clothing, dirt, and pose may change) and 0 if the shot judge does not see the pro-tagonist. The reference shot itself is excluded. Because the shots are fixed by the plan, a video that loses the protago-nist or breaks down cannot score by showing the protago-nist less often, and because pairs at any place and distance count, carrying the previous shot’s pixels forward does not help either. Revisit rates whether a returning shot shows the same place as the last visit and counts a return only if both shots are judged to be at their planned location, as the ge-ometric place consistency of StoryEngine [60] counts only shots in the right scene, so a model that stays in one place cannot score by looking the same. 

Face identity (MIR). MIR follows StoryEngine exactly (its App. D.8). It takes four evenly spaced frames per shot, including the first and last, and keeps InsightFace buffalo l detections at 640 ×640 with score ≥0.55. In shot order, each embedding joins the cluster with the most similar mean if the cosine is ≥0.45 and otherwise starts a new one, and single-detection clusters are dropped. MIR is the mini-mum over clusters of the mean cosine between detections from different shots, and 0 when no cluster spans two shots. We report MIR here rather than in Tab. 1 because it mea-sures faces only (two of our 25 protagonists are an ani-mal and a robot), it rewards videos that repeat nearly the same frames across shots, and it does not penalize a video that breaks down (Self-Forcing 0.400). Same protagonist is used in the main paper. With our memory, MIR is higher on both MiniMax-H3 generators (Tab. E3): by +0 .005

## F. Baselines 

Real-time baselines. Rolling Forcing supports a single prompt, so we split generation per shot, re-cache KV at prompt switches as in LongLive [74], and wrap RoPE after 1,024 positions (stories reach 1,764 latent frames). It takes 19.3 s per shot. The other Wan2.1-T2V-1.3B models use the same protocol: one continuous rollout per story, 42 latent frames per shot (10.3–10.5 s at 16 fps), only the current shot prompt, and one seed set before the first shot. Shot 0 of ev-ery model is identical to its official inference. Self-Forcing 

uses the official sampler (4 steps, 3-frame blocks) with the repository’s rolling KV cache of 21 frames (its train-ing context) and no sink. Cached frames are recomputed under each new prompt as for Rolling Forcing, and RoPE wraps after 1,024 frames (18.2 s per shot). Causal-Forcing 

is run with the authors’ long-video checkpoint, which uses the Rolling Forcing inference code (17.4 s per shot). Its 5-second chunkwise checkpoint, run like Self-Forcing, breaks down within about two shots (87.6% of its shots have se-vere artifacts). CausVid uses the repository’s long-video 23 script, with rollouts of up to 21 latent frames, each started from 3 overlap frames, and 3 steps. Rollouts never cross a shot boundary, so a new prompt starts the next rollout and re-encodes the overlap under that prompt (13.4 s per shot). 

SkyReels-V2 uses DF-1.3B-540P at 960 ×544 with official settings (30 steps, guidance 6, TeaCache 0.3): shot 0 is text-to-video and each later shot is a video extension of 160 frames (10 s at 16 fps) conditioned on the last 17 frames, with its own prompt (87.6 s per shot, one seed). As it is far from real time, its results are in Tab. F1 rather than in Tab. 1: it is below LongLive-2.0 with its built-in memory in state, location, and revisit, slightly above it in identity and same protagonist, and has the lowest imaging quality of all methods. All times are measured on one H100 (mean over 15 shots after a warm-up, FlashAttention-2, no compilation) and include decoding. The videos themselves were gener-ated on A100s, and the same timing scripts run on an A100 match the generation times within 1–3%. Self-Forcing and the chunkwise Causal-Forcing model degrade once the first frames leave the cache, as in their official single-prompt code, so their judge metrics should be read together with the artifact rate.

Long-horizon robot tasks. Generated robot data needs long videos in which the robot works through many steps while parts of the scene leave the view and come back. We take the first frames of 30 validation clips of RoVid-X [14], which cover one and two arms, grippers and hands, and head-mounted and fixed cameras. For each first frame, Gemini 3.8 Flash drafted a script of eight 8 s instructions (64 s in total), which we then edited by hand. The first in-structions finish the clip’s own task. Each script then hides one or two things and brings each back one to four instruc-tions later. A head camera turns away and back (20 return moments), or a drawer, fridge, box, or lid is closed and reopened, or an object is covered and uncovered (21 mo-ments). An instruction that brings something back never describes it, for example “pull the top left drawer open again and reach in for what you put there,” so only memory can tell the generator what to show. Each segment continues from the last frame of the previous one, so that the 64 s video is meant to be one continuous take, although the gen-erator can still cut on its own. Without memory, this frame is all that the generator knows about the scene. Unlike the main text, where the memory for a shot must be ready be-fore its prompt arrives (C1), each instruction here is avail-able one segment before it plays, as in a scripted robot task, and the agent uses it to choose pictures and rewrite it. This section therefore tests observation-based memory on robot videos, not C1. 

Agent. Unlike the open-loop agent of the main text, this agent observes the video, because a robot acts in one con-tinuous scene rather than in separate shots. Where an ob-ject ends up, or whether a drawer is still open, depends on the generated video rather than on the script, so the mem-ory has to be read from that video. As in the close-up test, it is an observation-based variant: its memory pictures are frames that the robot’s camera has already shown, or crops of them, so it needs no image model. After each segment, the agent looks at three of its frames. It describes the view, lists the visible objects with their position and look, and records whether each container is open or closed and what it holds. It also picks a frame to keep, a frame that shows the inside of an open container, and boxes for up to two objects. Code turns these observations into two parts of memory. A record of objects and containers keeps an object that was put into a closed container as hidden inside it. A bank of pic-tures holds one view per segment, container interiors, and the newest crop of each object, each with a caption and the segment it comes from. Before each segment, a router an-swers one narrow question about the next instruction: does something come back into view, because the camera turns back, a container is reopened, a cover is lifted, or an object is taken out? It agrees with the scripts’ annotations in 188 of 210 segments. Only when something comes back, the agent sees the bank as thumbnails and lists every picture of the returning place, container, or object. It pins the newest matching view and the newest close view (at most two pic-tures, Fig. G1) and rewrites the instruction so that it names what comes back and how it looked when last seen. Oth-erwise it pins nothing and only rewrites the instruction to name the objects with their look. Pinning only on returns matters: pictures pinned in almost every segment make the generator restore old states, for example a tube put into a drawer reappears on the cabinet. The agent was developed on one of the 30 episodes and then kept fixed for all runs.

Real time and parallelism. The closed loop still runs in parallel with generation. Failure cases. The remaining failures fall into three groups. First, the stored picture can be wrong. ## H. Entity Evolution and Limitations 

Entity evolution. Figure H1 shows how the entity images of the RL planner’s memory change over a story: a new version is drawn as an edit of the previous image when a prompt states a persistent change, and it shows only persis-tent attributes on a plain backdrop, with pose and action left to the next prompt. 

Failure cases and limitations. Memory follows the story up to the previous prompt, because it is built before the next prompt arrives (C3). Two cases follow from this. A persis-tent change that the current prompt states for the first time, such as a character shaving, is not yet in the memory im-ages of that shot, which can keep the earlier look until the agent has drawn the change for the following shots. A re-called place comes with the picture of its last visit. If a character has changed since, the cards state the new look, but an attribute that no card names can follow the earlier picture until the place is drawn again. Re-injecting updated memory within a shot, once its prompt has arrived, would address both cases and is left to future work. 

Framing. For every shot, the judge also decides whether the shot size, camera angle, and main subject agree with the planned camera and content ( framing match in the judge prompt of Sec. E). Re-judging agrees on 94.8% of shots, and the second judge agrees with κ = 0 .71 . None of the compared works scores framing. On LongLive-2.0, framing rises with our full system from 58.5% to 65.9% of shots (three seeds), but planned close-ups, a quarter of all shots, fall from 75.5% to 63.7%. Memory images show whole entities in medium or wide views and pull the gener-ator toward that shot size, so 78% of the remaining misses are rendered as medium shots. Memory is built before the prompt (C3), so it cannot be drawn at the shot size of the coming shot, whereas StoryEngine and our offline variants, which draw a keyframe or references after each prompt, reach 74–95% framing. Long text also competes with cam-era words: cards for every injected member cost 22.4 ∗ fram-ing points alone and 11.9 ∗ with images, whereas cards for the entities that the prompt names cost none ( −0.7 with the 35B planner, not significant).

## I. User Study 

Setup. Thirty-two volunteers from our research commu-nity took part, recruited by convenience sampling. Each judged ten stories of LongStory-Online: five comparisons on LongLive-2.0 (its built-in memory vs . our full system) and five on LongLive-H3 (independent shots, K/V carried across shots, and our full system), with the videos of Tab. 1 at seed 0. A comparison shows four shots spread over the story (first, one third, two thirds, and last), with the anony-mous versions side by side in a rotating order and a short note on what happens between the shots (Fig. I1). Method names and memory images are not shown. For each of four criteria, identity consistency, persistent state, location cor-rectness, and visual quality, participants pick the best ver-sion, mark a tie, or answer Cannot judge (missing visual evidence or playback failure). 

Ethics. Participation was voluntary and anonymous and could be stopped at any time. Every response includes informed consent, and the form stored no personal data. No formal IRB review was conducted, as the study was a minimal-risk perceptual evaluation of generated videos.
